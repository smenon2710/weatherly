# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

SkySpeak: Premium Weather Chat is an Android weather app (Kotlin + Jetpack Compose) that pulls forecast data from Open-Meteo (no API key) and optionally uses OpenRouter for an AI chat assistant. The app was formerly named Weatherly. The Play Store `applicationId` is `io.github.smenon2710.skyspeak`, but the Kotlin `namespace`, package (`com.example.weatherly`), and all `Weatherly`-prefixed class names are intentionally left unchanged — Google Play only requires `applicationId` to be unique, not the internal package name, so this was a low-risk one-line change rather than a full source-tree rename.

## Build & run

Open the project root in Android Studio (Quail or newer) and let Gradle sync, then run on a device or emulator via the IDE's run configuration. This is the primary, intended workflow.

**There is no `gradlew`/Gradle wrapper checked into this repo** — don't assume `./gradlew <task>` works; it won't, the file isn't there. If you need to drive a build from the command line (CI, an agent without IDE access, etc.), Android Studio has already cached the exact Gradle distribution `gradle/wrapper/gradle-wrapper.properties` asks for under `~/.gradle/wrapper/dists/`, and Android Studio bundles its own JBR — both are usable directly without installing anything system-wide:

```bash
export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"   # macOS path; adjust per OS
GRADLE_BIN=$(find ~/.gradle/wrapper/dists -path "*gradle-*-bin/*/gradle-*/bin/gradle" | head -1)
"$GRADLE_BIN" assembleDebug     # debug APK
"$GRADLE_BIN" bundleRelease     # signed release AAB (needs STORE_PASSWORD/KEY_PASSWORD in local.properties)
"$GRADLE_BIN" test              # unit tests (none yet; placeholder)
"$GRADLE_BIN" lint
```

This is exactly how the versionCode 9 release AAB was built and verified (`jarsigner -verify`, then a real sanity-install via `adb`) without ever opening Android Studio — see the Play Store launch status note below and the Launch Checklist in `PLAYSTORE_LAUNCH.md`.

## API key setup

Copy `local.properties.template` to `local.properties` (already git-ignored) and fill in:

```
sdk.dir=/path/to/your/Android/sdk
OPENROUTER_API_KEY=sk-or-...   # optional — quick-suggest chips work without it
OPENROUTER_MODEL=openrouter/free   # optional override; any OpenRouter model ID works
```

Both values are injected at build time into `BuildConfig.OPENROUTER_API_KEY` and `BuildConfig.OPENROUTER_MODEL`. If no key is present at build time, users can enter one directly in the chat screen; it is stored in `SharedPreferences` via `PreferencesStore`.

## Architecture

**Single-activity, three-screen app.** `MainActivity` holds a `WeatherViewModel` (activity-scoped) and dispatches between `WeatherScreen`, `ChatScreen`, and `SettingsScreen` via `AnimatedContent` keyed on a private `Screen` enum (`WEATHER`, `CHAT`, `SETTINGS`). `WeatherViewModel` exposes `themePreference: StateFlow<ThemePreference>` (read at the `MainActivity` root to pick light/dark/system for `WeatherlyTheme`) so `SettingsScreen` can change it. `SettingsScreen`/`SettingsViewModel` also own unit-system switching, on-device OpenRouter key/model management (the key field is write-only — `SettingsViewModel` never echoes the stored secret back), and a "Rate on Google Play" deep link with a browser fallback.
(A fourth screen, `RadarScreen` — a RainViewer/OSMDroid precipitation map — existed briefly but was removed as low-value; see git history if reviving it. Its `osmdroid` dependency, `ACCESS_NETWORK_STATE` permission, and the `@JsonClass`-wide ProGuard rule it required are gone with it.)

**Data layer:**

| Class | Role |
|---|---|
| `NetworkModule` | Singleton object wiring five Retrofit clients: Open-Meteo forecast, Open-Meteo geocoding, Open-Meteo air quality, OpenRouter, and NWS (`api.weather.gov`, for active weather alerts). Exposes `makeStreamingCall(Request)` for raw SSE calls. No DI framework. HTTP logging is added via the `OkHttpClient.Builder.addDebugLogging()` extension, which has two implementations in build-type-specific source sets — `src/debug/java/.../DebugLogging.kt` (adds `HttpLoggingInterceptor`) and `src/release/java/.../DebugLogging.kt` (no-op). This is required, not just cosmetic: `logging-interceptor` is a `debugImplementation` dependency, so a runtime `if (BuildConfig.DEBUG)` guard alone would still fail to *compile* in release (the import wouldn't resolve on that classpath). The NWS client carries its own OkHttp interceptor setting a `User-Agent`/`Accept` header — NWS throttles requests without a real identifying `User-Agent`. |
| `WeatherRepository` | Single source of truth. Fetches forecast + air quality + NWS alerts in parallel (`coroutineScope`/`async`). The alerts fetch is wrapped in `runCatching { }.getOrNull()` — NWS is US-only and has no key of its own, so a failure or an out-of-coverage point (empty `features` array) must never fail the overall weather fetch. 30-minute in-memory cache keyed by `"lat,lon,units"` covers `WeatherData.alerts` too, no separate cache. See "Weather alerts" below for the mapping/severity-inference details. Also requests Open-Meteo's `rain`/`showers`/`snowfall` fields (current, hourly, daily) separately from the generic `precipitation`/`precipitation_probability` fields, so callers can tell rain from snow using real data instead of guessing from the WMO code — see the snowfall-unit and precip-type entries in Key invariants. |
| `ChatRepository` | Streams OpenRouter responses token-by-token via SSE (`askStreaming`) and simulates the same feel for rule-based answers (`simulateStreaming`). Both return `Flow<String>`. Retries once on HTTP 429. All requests include `HTTP-Referer` and `X-Title` headers for OpenRouter log attribution. `systemPrompt()`'s `weatherBrief()` prepends any active NWS alerts (event, severity, expiry) to the WEATHER DATA block, and the rules explicitly tell the model to weigh them and volunteer them even when not asked directly (e.g. mention a Winter Weather Advisory on a driving question). `weatherBrief()` reports rain and snow separately (e.g. `"snowing: 1.2 cm"`, `"(2.1 cm snow)"` next to an hour/day) rather than one type-agnostic `precip` figure, and the system prompt explicitly tells the model a `"% precip"` reading alone doesn't imply rain. |
| `ForecastCache` | Persists the last successful `WeatherData` as JSON in `SharedPreferences` (`forecast_cache`). `WeatherViewModel.init` loads it synchronously so the app opens instantly offline. Replaced by fresh data on every successful network fetch. |
| `PreferencesStore` | `SharedPreferences` wrapper for unit system, saved places, selected place, on-device OpenRouter key/model, and the tracked-alert list used for resolution detection (see "Alert resolution tracking" below). |
| `WeatherAdvisor` | Pure object (no network). Answers six hard-coded intents (UMBRELLA, JACKET, WALKING, DRIVING, HIKING, CLOTHING) locally from the current `WeatherData`. `Ctx.isSnowy` (real `currentSnowfall`/`hourlySnowfall` data, falling back to `isSnowOrIce(code)`) is checked before any rain-percentage logic in every intent — `umbrella()` used to recommend an umbrella on snow days because its rain-percentage branch fired off `precipitation_probability` alone, which doesn't distinguish rain from snow. |
| `MoonCalculator` (`util/`) | Pure object. Computes lunar phase from Julian date arithmetic (reference JD 2451550.260, synodic month 29.530588853 days). Exposes `phase(y,m,d): Double` (0=new, 0.5=full), `phaseName(phase)`, `illuminationPct(phase)`, and `nextEvent(phase): Pair<String,Int>` (label + days). |

**UI layer:**

- `WeatherViewModel` — `AndroidViewModel` exposing `StateFlow<WeatherUiState>`. On `init`, loads `ForecastCache` synchronously so the screen is never blank on cold start. Handles location resolution (falls back to `LocationProvider` when no place is selected), unit switching, city search, and pull-to-refresh. `WeatherUiState.Success` carries a `cachedAt: Long?` timestamp; non-null means the data came from cache and triggers a "Showing data from Xm ago" label. Background refreshes keep existing data visible (only the spinner changes).
- `WeatherScreen`'s location-permission `rememberLauncherForActivityResult` callback calls `viewModel.load(background = state is WeatherUiState.Success)` rather than an unconditional cold load. The `LaunchedEffect(Unit)` that triggers the permission request re-fires every time `WeatherScreen` re-enters composition (cold start, and every return from Chat/Settings since `AnimatedContent` disposes/recomposes the screen). Since the permission is normally already granted, the callback fires almost immediately — a cold load there would flash existing on-screen content back to a full `Loading` state before the refetch completes. This mirrors the `ON_RESUME` effect's existing `if (state is WeatherUiState.Success)` guard.
- `ChatViewModel` — Exposes `messages`, `sending`, and `streamingText: StateFlow<String>`. Accumulates SSE/simulated chunks into `_streamingText`; on completion moves the full text into `_messages`. `clear()` cancels any in-flight stream job. `hasKey: Boolean` is a `get()` property that returns true when an API key is available (on-device or build-time).
- `ChatScreen` empty state — when `messages.isEmpty()`, shows three tappable example query rows (each calls `onQueryClick` to populate the input field). When `chatViewModel.hasKey` is false, appends a subdued "Tip: add your OpenRouter key" note.
- `ChatScreen` suggestion chips — six `AssistChip`s in a `LazyRow` above the input field. `suggestionTint(intent: AdviceIntent): Color` (private, non-composable) maps each intent to a distinct accent: UMBRELLA → Cyan, JACKET → Purple, WALKING → Green, DRIVING → Amber, HIKING → Teal, CLOTHING → Coral. Each chip gets `containerColor = tint.copy(alpha = 0.14f)` so chip domains read at a glance without being visually loud.
- `WeatherScreen` / `ChatScreen` / `SettingsScreen` — Compose screens consuming the ViewModel via `collectAsStateWithLifecycle`.
- `ui/components/` — Reusable Compose functions (header, hourly row, daily list, metric tiles, detail sheets, `WeatherBackground`).
- `ui/theme/` — Material 3 color scheme, typography, `WeatherlyTheme`.

**`WeatherBackground` (`ui/components/WeatherBackground.kt`):** Full-screen animated backdrop behind the entire scrolling `WeatherScreen` content (not just the hero) — an Apple-Weather-style per-condition scene, replacing the old hero-only static gradient. A private `Scene` enum (26 values, covering Clear/Cloud, Liquid Precip, Frozen Precip, Atmospheric Obscurations, and Convective/Severe categories) is chosen by `classify()` from real data only, never decoration for its own sake:

- WMO `code` (extended beyond the coarser ranges `WeatherRepository`/`WeatherAdvisor` use, to also split out freezing rain/drizzle (`56/57/66/67`), snow grains as sleet (`77`), and thunderstorm-with-hail (`96/99`) from plain thunderstorm (`95`)).
- `cloudCoverPct` splits WMO's single "overcast" bucket into `MOSTLY_CLOUDY` (65–89%) vs `OVERCAST` (≥90%) — a distinction the 4-value WMO code alone can't express.
- `visibility` (unit-aware — converts mi→km before comparing, since a raw-mile reading against a km threshold would mislabel every imperial user's fog) splits `MIST` from `FOG` at the standard ~1 km meteorological threshold; missing visibility data defaults to `FOG` (the denser reading), not `MIST`.
- `aqi` still tints `FOG` warmer/browner toward "smoky" past 100 (no separate smoke WMO code exists), and now also independently triggers `HAZE` on an otherwise clear/cloudy day (no fog code required) once `aqi > 100`.
- `TORNADO` and `HURRICANE` have no WMO forecast code at all — `classify()` instead checks active `WeatherData.alerts` for NWS `event` text containing "Tornado" / "Hurricane" / "Tropical Storm", which is real signal NWS actually issues, checked first (overrides every other input, most severe wins).
- `DUST_STORM` and `VOLCANIC_ASH` are a deliberate exception: no code, no alert type, no other signal Open-Meteo or NWS provides for either, so `classify()` never returns them — they're implemented (own enum value, own `drawDustStorm`/`drawAsh` renderer) but genuinely unreachable today, per an explicit product decision to have the visuals ready ahead of a future data source rather than fake a trigger.
- A separate `severeWind` boolean (real `windKmh`/`windGustKmh`, ≥45 km/h gust) layers `drawWindStreaks` on top of *any* scene except Tornado/Hurricane (which already imply extreme wind) — this is what makes `SNOW_HEAVY` + high wind read as a blizzard, without a dedicated `BLIZZARD` scene.

One shared `timeMs` clock (`withFrameMillis` in a `LaunchedEffect` loop) drives every particle; positions are pure functions of `(timeMs, per-particle seed)` computed inside a single `Canvas`'s draw phase, not composition — reading `timeMs` only there means each tick redraws just that Canvas, not the whole screen. Per-particle seed lists (`Seed(a,b,c,d): four random floats`) are generated once per scene via `remember(scene)`, never regenerated per frame, so particles don't jitter. Renderers, each reused across multiple scenes rather than one bespoke illustration per scene: `drawRain` (angled streaks, `RainIntensity` tiers: DRIZZLE/LIGHT/MODERATE/HEAVY), `drawHurricaneRain` (near-horizontal sheets, a distinct function rather than a rain-intensity tier so normal rain can't accidentally inherit hurricane-grade slant), `drawSnow` (`SnowIntensity` tiers, sinusoidal side-sway), `drawSleet` (fast slanted streaks + static bounce-tick marks), `drawHail` (falling spheres + static impact marks), `drawFogBands` (drifting translucent bands, shared by `MIST`/`FOG`/`DUST_STORM`), `drawHaze` (mostly-static warm horizon wash — deliberately not drifting like fog, since haze is a stagnant-air tint), `drawClouds` (drifting 3-circle silhouettes; `OVERCAST` instead draws one flat full-canvas gray rect, not more cloud blobs, per the "texture-blocked sheet, no shadows" brief), `drawStars`, `drawSunGlow`, `drawMotes` (golden-hour-only "beautiful evening" extra layer), `drawThunderFlash`, `drawGroundWash` (a bottom-of-screen translucent strip standing in for wet/snowy/icy ground — used by `RAIN_HEAVY`, `SNOW_MODERATE`/`HEAVY`, `SLEET`), `drawIceSheen` (a moving specular highlight for freezing rain's "high-gloss" look, distinct from the flat-alpha ground wash), `drawAsh` (a darker/faster/smaller cousin of `drawSnow`), `drawTornado` (the one genuinely bespoke shape: stacked wobbling ellipses tapering to a point, rotating via a `timeMs`-driven angle, plus orbiting debris dots), `drawWindStreaks`. The base gradient is `conditionGradient` (unchanged) stretched to the full screen rather than just the hero height.

**Particle color, not just alpha, must be theme-aware.** `drawRain`/`drawHurricaneRain`/`drawSnow`/`drawSleet`/`drawHail`/`drawIceSheen`/`drawWindStreaks` all take an `ink: Color` param computed once in `WeatherBackground` (`rainInk`, `snowInk`, `sleetInk`, `hailInk`, `windInk`, `iceSheenInk`, `snowWashInk`) rather than hardcoding `Color.White`. Dark mode keeps white — it pops against the dark gradient stops. Light mode uses the app's existing rain/snow "slate blue" tip-tone family (see `tipColors()`) instead, e.g. `rainInk = Color(0xFF3F5670)` — **lowering alpha alone cannot fix this**, since white-on-pale-pastel is a wrong hue, not just a wrong opacity, and was invisible enough in practice that the whole animated background read as "not changing with the weather" in light mode even though `Scene`/the base gradient were both classifying and shifting correctly the whole time (confirmed via a real device screenshot during testing). `drawStars` and `drawThunderFlash` are the only two renderers that keep plain `Color.White` unconditionally — correctly, since stars only render at night (when `conditionGradient`'s stop is dark navy in *both* app themes) and a lightning flash is inherently a white light burst regardless of theme.

Cards (`GlassCard`) stay fully opaque over this background — a translucent "frosted glass" card fill (`LocalTranslucentCards`, alpha-blending `surface` at ~0.72–0.78) was tried and reverted. Real glassmorphism needs actual blur (`RenderEffect`, API 31+ only), not just alpha; alpha-blending a near-white light-mode fill over this busy animated background instead produced a visibly patchy card with seams at the rounded corners — worse in light mode (dark-on-dark blends forgivingly against a dark scene; light-on-colored doesn't) — confirmed via a real device screenshot during testing. `WeatherBackground` still shows through in the hero and in the gaps/margins around cards; cards themselves are solid, matching every other screen.

**Weather alerts (`WeatherAlert` / `AlertSeverity` in `data/model/WeatherData.kt`):** Official advisories from the National Weather Service (`api.weather.gov/alerts/active?point=lat,lon`), US coverage only, free, no key. `WeatherRepository.mapAlerts()` builds the domain list from the raw `NwsAlertsResponse`:

- Filters to `status == "Actual"` (excludes Test/Exercise/Draft products NWS also publishes through this feed), dedups by `id`.
- **Same-event/same-area collapse:** NWS can independently issue multiple non-linked products for the identical event and area — confirmed live for Franklin Park, NJ: two separate Air Quality Alert issuances covering the exact same 3 UGC zones simultaneously, a day apart, neither referencing the other (`references: []`, `messageType: "Alert"` not `"Update"`). This is a rolling day-ahead reissuance pattern (each ~30hr window overlapping the previous one), not an error, but showing both raw CAP products reads as a duplicate — NWS's own consumer-facing tools show only the current one. `mapAlerts()` groups by `(event, areaDesc)` (falling back to that alert's own `id` when either is null, so incomplete-data alerts never accidentally collapse into each other) and keeps only the most-recently-`sent` entry per group, via `parseInstantOrMin()` (the `Instant.MIN`-default counterpart to `parseInstantOrMax()`, so a missing `sent` value loses rather than wins the comparison).
- **Severity inference:** NWS tags nearly every Air Quality Alert `severity: "Unknown"` — its CAP severity taxonomy has no air-quality category. `parseSeverity()` falls back to parsing the description for EPA's standardized "Code Red/Orange/Purple/Maroon" AQI names (the literal terms every state environmental agency uses nationwide for these alerts) when `event` contains "Air Quality" and CAP severity is absent, defaulting to `MODERATE` (never the calmest tier) if no code keyword matches. Without this, a "Code Red...unhealthful for the general population" alert would render in the same visual tier as a Small Craft Advisory.
- **Sort order:** primarily by severity (most severe first), with effective-time as a tiebreaker — NWS can have multiple same-severity products active simultaneously (e.g. an Air Quality Alert for today and a separate one for tomorrow), so ordering would otherwise depend on arbitrary API array order.
- **`ends` vs `expires`:** `expiresLabel` prefers `p.ends` (when the hazard itself is expected to end) over `p.expires` (when the CAP *message* expires, which for long-duration products like a multi-day Flood Watch is often much sooner than the actual hazard window and reads as misleadingly early). Falls back to `expires` for shorter products that don't set `ends`.
- **`formatNwsTime()` includes day context**, not just clock time (e.g. `"Tomorrow, 8:00 PM"` / `"Jul 18, 8:00 PM"`, plain `"8:00 PM"` only for today) — NWS legitimately issues multiple alerts sharing an identical event name for one point (day-by-day reissuance without linking via `references`, or overlapping zone coverage for border locations; confirmed live for Franklin Park, NJ, which had 3 simultaneously-active "Air Quality Alert" entries with distinct IDs). Time-only formatting made two such alerts effective/expiring at the same clock time on different days render as literally identical text.
- **Text normalization:** `normalizeNwsText()` collapses NWS's hard-wrapped-at-80-columns literal newlines into spaces (preserving genuine blank-line paragraph breaks) — rendered verbatim, `description`/`instruction` would show as choppy short lines instead of normal paragraph reflow.
- `WeatherData.alerts: List<WeatherAlert> = emptyList()` — the default is required, not cosmetic: `ForecastCache` deserializes old cached JSON (written before this field existed) via Moshi's reflective adapter, which only fills a missing key from a constructor default.

UI: `AlertBannerList` (`ui/components/WeatherComponents.kt`) is a single-line severity strip, not a `GlassCard` — left 4dp accent bar + subtle tint in the alert's severity color, the same left-accent-bar language `TipBanner` already established elsewhere in the app, rounded only on the right corners. This replaced an earlier full-card treatment (icon + bold title + subtitle + chevron, four lines tall) after user-reported testing found it took over too much of the screen with multiple active alerts, on top of the `DetailSheet.AlertList` cropping bug below. Two *earlier* revisions had already tried to make the card visually exceptional (full-bleed/square to read as a "system notice"; placed above the hero before any app branding) and both were reverted after feedback that it looked out of place or was mistakable for an OS notification — this redesign is a different axis of change (smaller, not differently-shaped) and doesn't reopen that: same shape language as `TipBanner`, just sized down, still living in the ordinary card-flow position (first, right after the hero) rather than anywhere exceptional. The leading `AccountBalance` icon (a government building, not a warning triangle) is what's left of the old spelled-out "NATIONAL WEATHER SERVICE" eyebrow — same icon, so it still reads as "official source" without a dedicated label line. Tapping the strip opens `DetailSheet.Alert` directly when there's exactly one active alert, or `DetailSheet.AlertList` (a chooser) when there's more than one; a `SeverityDotCluster` — one small dot per alert, each colored by *that* alert's own severity, capped at 4 with a "+N" text fallback — renders next to the event name so someone can gauge overall risk ("one rust dot, one gold dot" = one severe hazard, one advisory) without tapping in. `ResolvedAlertCard` uses the identical strip treatment (sage green, checkmark icon) for visual consistency between the two — an odd pairing otherwise, a shrunk "urgent" indicator sitting above a full-size "all clear" card.

`DetailSheet.AlertList` used to stack every active alert's full `AlertDetailContent` (description, instructions, badges) in one non-scrolling `Column` — with 2-3 alerts this reliably exceeded the sheet's height and silently cropped the 2nd/3rd alert with no way to scroll to it, since `DetailSheetContent`'s root `Column` had no scroll modifier (`ModalBottomSheet` doesn't add one automatically; every *other* sheet type happened to fit within the sheet height by chance, which is why this was latent rather than immediately obvious). Fixed two ways: `DetailSheetContent` now wraps its root `Column` in `Modifier.verticalScroll(rememberScrollState())` as a general safety net for every sheet type, and `DetailSheet.AlertList` itself no longer shows full content at all — it's a tappable summary-row list (`AlertSummaryRow`: severity dot, event name, `alertTimeWindow()`), and tapping a row calls the new `DetailSheetContent(sheet, onAlertSelected: (WeatherAlert) -> Unit)` callback (wired in `WeatherScreen.kt` to `sheet = DetailSheet.Alert(it)`) to open that one alert's full view — since `ModalBottomSheet` stays open and only its content swaps, this reads as drilling into the chooser rather than the sheet closing and reopening.

`alertTimeWindow()` is a concise, single-line, never-truncated stand-in for NWS's own (often long) `headline` prose — e.g. `"12:00 PM – Jul 18, 8:00 PM"` — used by both the compact strip and `AlertSummaryRow`. The raw `headline` is often long enough to ellipsize before its "until X" time is visible, which made two distinct same-named alerts (see the `formatNwsTime` note above) look like duplicates at a glance; `headline` remains the fallback only when both `effectiveLabel` and `expiresLabel` are null. `AlertDetailContent` (the full single-alert view, reached via `DetailSheet.Alert` from either entry point) shows severity, `AlertBadge` pills for urgency/certainty (NWS's `"Unknown"` value is treated as absent, not rendered), description, instructions, and the effective/in-effect-until times. `alertColors(severity)` collapses the 5-value enum to 3 visual tiers (Critical = Extreme/Severe, Advisory = Moderate, Info = Minor/Unknown) — Critical is the one genuinely new hue in the app (warm rust/oxblood, not a clinical safety red); Advisory reuses the launcher icon's warm-gold; Info reuses the existing `tipColors()` RAIN tone verbatim.

**Alert resolution tracking:** `WeatherViewModel.trackAlertChanges()` runs after every successful fetch (foreground or background), diffing the current alert IDs against `PreferencesStore.getTrackedAlerts()` (a persisted `List<TrackedAlert>` — just `id` + `event`, not the full alert). Any previously-tracked ID missing from the new fetch is "resolved" and gets queued into `WeatherViewModel.resolvedAlerts` (in-memory `StateFlow`, not persisted across process death — an unresolved-but-undismissed notice simply won't reappear if the app is killed before the user sees it, since the tracked set is already overwritten to the current state). `ResolvedAlertCard` renders each one as a calm, dismissible, sage-green acknowledgment ("$event has ended") — deliberately opposite `AlertBannerList`'s severity styling, since this is reassurance, not an ongoing hazard. This exists because the app previously went silent when an alert cleared, giving no confirmation to a user who'd seen the earlier warning that the danger had actually passed (flagged by user feedback). Resolved cards render below any currently-active alert (an ongoing hazard always outranks an acknowledgment) but above `HourlyCard`. `selectPlace()`/`selectCurrentLocation()` call `resetAlertTracking()` to clear both the persisted and in-memory state on a location change — a tracked alert from the previous place isn't a real "resolution" for the new one.

**Widget:** `WeatherWidget` (Jetpack Glance) fetches weather independently at system-scheduled update intervals. `WeatherWidgetReceiver` wires it into the manifest (`android:exported="true"` — required for APPWIDGET_UPDATE broadcast delivery). The widget creates its own `WeatherRepository` instance; if a network fetch fails or location is unavailable it falls back to `ForecastCache` so it always shows real data after the first app open. `WeatherViewModel` calls `WeatherWidget().updateAll(getApplication())` after every successful fetch to keep the widget in sync immediately.

- **Size-aware layouts** — `sizeMode = SizeMode.Responsive(setOf(SMALL, MEDIUM, WIDE, LARGE))`. Glance picks the largest declared breakpoint that fits the actual widget size; `WidgetContent` dispatches on `LocalSize.current`:

  | Constant | DpSize | Cell grid | Content |
  |---|---|---|---|
  | `SMALL` | 110×50 dp | 2×1 | Emoji + current temp (22 sp Bold), centered |
  | `MEDIUM` | 110×110 dp | 2×2 | Location header + chrono-dynamic vertical stack |
  | `WIDE` | 250×50 dp | 4×1 | `emoji temp° · location` + compact next-4-hour text (`isDay`-aware emoji) |
  | `LARGE` | 250×110 dp | 4×2 | `LargeHeader` (2-column) + `HourlyStrip` (up to 5 cells, `isDay`-aware emoji) |

  `weather_widget_info.xml` declares `minWidth="110dp"`, `minHeight="40dp"`, `targetCellWidth="2"`, `targetCellHeight="2"`, `resizeMode="horizontal|vertical"`.

- **Chrono-dynamic content** — `currentTimeOfDay()` reads `Calendar.HOUR_OF_DAY`. MEDIUM and LARGE layouts branch on the result:

  | TimeOfDay | Hours | Focus |
  |---|---|---|
  | `MORNING` | 5–10 | Today's high temp (hero) + rain probability |
  | `DAYTIME` | 11–17 | Current temp (hero) + condition + H/L |
  | `NIGHT` | 18–4 | Tomorrow's H/L (hero) + tomorrow's condition |

- **Material You colors** — `resolveWidgetColors(context)` runs outside the composable (no `GlanceTheme` dependency needed). On API 31+ reads `android.R.color.system_accent1_100/700/900` via `ContextCompat.getColor` and detects dark mode from `context.resources.configuration.uiMode and Configuration.UI_MODE_NIGHT_MASK`. Light: accent1-100 bg + accent1-900 text. Dark: accent1-700 bg + accent1-100 text. Pre-API 31 falls back to the app's static dusty-blue palette. Returns `WColors(bg, textPrimary, textSecondary: ColorProvider)`. Only the `ColorProvider(Color)` single-argument overload is used — `ColorProvider(day, night)` does not exist in `glance-appwidget:1.1.0`.

**Launcher icon:** Adaptive icon (`mipmap-anydpi-v26/`) — warm-gold sun glyph (`#E0B15C`) on deep navy (`#0F1923`), with three concentric speech-wave arcs to the right of the sun (radii 20/25/30 dp, fading opacity) representing the "speak" dimension. XML-only; no PNG fallbacks needed since `minSdk = 26`.

**WMO weather codes** are mapped to emoji and text in `util/WeatherIcon.kt`. All temperature/wind/precip values in `WeatherData` are stored in the user-selected unit (they come back from Open-Meteo already converted); `WeatherAdvisor` converts back to metric internally for threshold comparisons.

**`HourEntry`** carries `hourLabel`, `tempC`, `icon` (WMO code), `isDay: Boolean`, and `precipChance: Int?`. `isDay` is computed per-hour in `WeatherRepository` via ISO-string comparison (`hourTime >= sunriseStr && hourTime < sunsetStr`) against the day's sunrise/sunset strings from the daily block. `HourlyCard` passes `h.isDay` to `WeatherGlyph` so each hour renders the contextually correct day or night icon. `HourlyCard` wraps its `LazyRow` in a `Box` with `rememberLazyListState`; a 28dp right-edge gradient fade (`Color.Transparent → colorScheme.surface`) is always overlaid as a scroll affordance, and a 20dp left-edge fade appears once `firstVisibleItemIndex > 0` or `firstVisibleItemScrollOffset > 0`.

## UI theme & branding

**Logo:** Two-tone text wordmark — an `AnnotatedString` in `WeatherScreen.kt` rendering `"sky"` in `TextSecondary` and `"speak"` in `TextPrimary`, at 20 sp, `FontWeight.Light`, `letterSpacing = 5.sp`. The color split is subtle in light mode (muted slate → near-black) and more expressive in dark mode (slate → near-white). Colors are captured as local vals before the `buildAnnotatedString` block so they are read in composable scope. Do not reintroduce image assets or collapse the two spans into a single `color` parameter.

**Colour scheme (`ui/theme/Theme.kt`):**
- Light: background `#F4F1EB` (warm cream), surface `#FDFCFA` (barely warm white), primary `#6B86A3` (dusty blue).
- Dark: background `#0F1923` (deep navy), surface `#1A2530`, primary `#7FA3C2`.
- `AppBackground`, `TextPrimary`, `TextSecondary` are `@Composable` vals in `WeatherComponents.kt` resolved from `MaterialTheme.colorScheme` — always use these rather than hardcoded colours.

**Condition gradient (`conditionGradient` in `WeatherComponents.kt`):** A `@Composable` function that maps a WMO weather code + `isDay` flag to a two-stop `List<Color>`. The first stop is a sky tone (blue for clear day, indigo for thunder, slate for rain, etc.); the second stop is always `MaterialTheme.colorScheme.background` so the gradient fades seamlessly into the card area. Additionally, `Calendar.HOUR_OF_DAY` is read and the sky color is `lerp`-blended with a time-of-day tint: 5–6 AM → warm apricot (`#E8936A`, 18%), 5–6 PM → amber (`#D4A44C`, 15%), 7–8 PM → dusty violet (`#A0668A`, 20%). All other hours receive no tint. Used as the base layer of `WeatherBackground` (stretched to the full screen, with particle scenes drawn on top) via `Brush.verticalGradient`. Dark-mode stops are deliberately lighter/more saturated than a naive darkened version of the light-mode stop — the dark background (`#0F1923`) is itself very dark, so a naive darken puts most conditions within a few RGB steps of the background and the gradient reads as flat/invisible. Each dark stop is calibrated for a visible lift off the background, same as the light-mode stops are clearly lifted off the cream background.

**`GlassCard` (`ui/components/WeatherComponents.kt`):** The shared card wrapper. Shadow adapts per theme: `1 dp` in light (airy), `6 dp` in dark (depth). Border opacity likewise adapts. All major content sections (hourly, daily, metric tiles) use `GlassCard`. Fill is always opaque `colorScheme.surface`, overridable via the `fill` param (e.g. `AlertBannerList`'s severity tint) — see `WeatherBackground` above for why a translucent fill over the animated background was tried and reverted.

**Metric tile system (`MetricsGrid` in `WeatherComponents.kt`):** Five distinct composables:

| Composable | Used for | Visual |
|---|---|---|
| `PrimaryStatCell` | UV Index, Humidity, Wind (compact strip) | Equal-weight column inside a single top `GlassCard`: label at 10sp SemiBold uppercase, value at 22sp Bold in accent color, optional sub at 11sp `TextSecondary`. Each cell is individually `clickable` and opens the full detail sheet. |
| `ArcGaugeTile` | AQI, Pressure, Visibility | 88dp Canvas arc (240° sweep, 150° start), track + filled portion keyed by `gaugeFraction` in `MetricTileData` |
| `SparklineTile` | Feels Like, Precipitation | Area sparkline with vertical gradient fill, animated "Now" dot at index 0 (slow pulse: scale 1.0→1.4, 1.2 s, reverse, via `rememberInfiniteTransition` at the top of the composable — declared unconditionally before `GlassCard`; captured as `capturedPulse` before the Canvas block), time axis labels. Draws a dashed vertical line + "tmrw" label at `MetricChart.dayChangeIndex` when the data spans midnight. |
| `SunTile` | Sunrise/Sunset | Flexible-height semicircle arc (min 64dp, scales with card) showing elapsed portion of the day or night (progress-filled), golden-hour glow zones near both horizon endpoints. Day mode: arc from sunrise → now → sunset; sunrise/sunset times shown below. Night mode: arc from sunset → now → tomorrow's sunrise; tonight/tomorrow times shown below. The Sunrise+Visibility row uses `Modifier.height(IntrinsicSize.Max)` + `fillMaxHeight()` so both cards match the taller one's height and the arc grows proportionally. |
| `MoonTile` | Moon Phase | Full-width card with a 72dp Canvas moon-phase illustration on the left and phase name / illumination % / next-event countdown on the right. |

`MetricsGrid` layout order: primary compact strip (UV | Humidity | Wind, single `GlassCard`) → Feels Like (SparklineTile, full-width) → Precipitation (SparklineTile, full-width) → `SectionLabel` "ATMOSPHERE" (Air icon, Teal) → AQI + Pressure row (ArcGaugeTiles) → `SectionLabel` "SKY" (WbTwilight icon, Orange) → Sunrise + Visibility row → Moon Phase (full-width).

`gaugeFraction` values: UV `(uv/11).coerceIn(0,1)`, AQI `(aqi/200).coerceIn(0,1)`, Humidity `hum/100`, Pressure `((hPa-960)/90).coerceIn(0,1)`, Visibility `(km/max).coerceIn(0,1)` where max is 10 mi or 16 km. For Moon Phase, `gaugeFraction` stores the phase fraction (0.0 = new moon, 0.5 = full moon) as computed by `MoonCalculator.phase()`.

**`MetricChart.dayChangeIndex`:** `Int?` field on `MetricChart`. Set by `buildMetricTiles` to the index of the first `"12 AM"` label in `d.hourLabels` (null if data doesn't span midnight). Consumed by `SparklineTile` to draw a dashed vertical line at the day boundary, and by `WindDetailContent`, `FeelsLikeDetailContent`, and `PrecipDetailContent` to draw the same marker in their detail-sheet charts. The time-axis label at that index is replaced with `"tmrw"` in accent color.

**`SunTile` data encoding:** `MetricTileData.value` holds the sunrise time string. `MetricTileData.sub` encodes `"Sunset HH:MM|TomorrowRise HH:MM"` — `SunTile` splits on `|` and parses each key-value pair. `parseTimeHour(time: String?)` handles both 24-hour strings and 12-hour AM/PM strings.

**`MoonTile` / `drawMoonPhase`:** `drawMoonPhase(center, r, phase, litCol, darkCol)` is a private `DrawScope` extension in `WeatherComponents.kt`. Draws the illuminated lunar disk using an arc-based path: a semicircle on the lit side closed by an ellipse arc representing the terminator. `termX = r * cos(phase * 2π)` gives the terminator x-offset. Waxing (phase < 0.5): left shadow half-circle + conditional ellipse; waning (phase ≥ 0.5): right shadow half-circle + conditional ellipse. Short-circuits to solid dark disk at new moon (phase < 0.02 or > 0.98) and solid lit disk at full moon (phase 0.48–0.52).

**Detail sheet system (`DetailSheet` sealed interface, `DetailSheetContent`):** Tapping any metric tile opens a bottom sheet. `DetailSheet.Metric` carries optional fields `windDir: String?`, `windGust: String?`, `hourlyActualTemps: List<Int>?` for enriched views. `DetailSheetContent` dispatches on `sheet.title`:

| Title | Composable | Content |
|---|---|---|
| `"Wind"` | `WindDetailContent` | Speed/gust row, 164dp compass rose (Canvas tick marks + direction needle via `windDirToAngle()`), color-coded hourly intensity bars via `windIntensityColor()`, day-boundary dashed line |
| `"Feels like"` | `FeelsLikeDetailContent` | Warmer/cooler pill, 160dp dual-line Canvas chart (solid feels-like + dashed actual temp + shaded gap) using `PathEffect.dashPathEffect`, day-boundary dashed line |
| `"Precipitation"` | `PrecipDetailContent` | 128dp color-coded probability bars via `precipIntensityColor()`, dashed 30%/70% threshold guidelines, day-boundary dashed line. Chart label is the type-neutral "HOURLY PRECIPITATION CHANCE" (not "RAIN") since `precipitation_probability` doesn't distinguish rain from snow — the headline value/icon above the chart carry the real type, from `buildMetricTiles`' rain-vs-snow logic (see Key invariants). |
| `"Moon Phase"` | `MoonDetailContent` | 110dp moon-phase Canvas illustration, phase name + illumination % + next-event countdown, phase-cycle description paragraph |
| anything else | `DefaultMetricContent` | Value + description + `MetricBarChart` |

Helper functions (private, in `WeatherComponents.kt`): `windDirToAngle(dir: String?): Float` maps all 16 compass points to degrees; `windIntensityColor(speed)` and `precipIntensityColor(prob)` return a `Color` from a 5-stop intensity palette; `parseTimeHour(time: String?): Float?` handles both 24-hour and AM/PM time strings. `@Composable` color values (`TextPrimary`, `TextSecondary`) must be captured as local `val`s before entering any Canvas `DrawScope`.

**`TipBanner`:** Left-border annotation style — 4dp accent bar on the left edge, very subtle tint (`fg` at 8–10% alpha), rounded only on the right corners. Reads as editorial context rather than an alert. `TipBanner` composables are **not rendered in the hero section** of `WeatherScreen` — they were removed to eliminate the "multiple summaries with different tinted backgrounds" visual. The single lookahead pill inside `CurrentHeader` is the only hero-area summary.

**`WeatherGlyph`:** Accepts `isDay: Boolean = true` and an optional `contentDescription: String?` (defaults to `wmoText(code)`). Pass `null` for decorative instances where adjacent text already carries the meaning. `glyphFor(code, isDay)` dispatches WMO codes to night variants when `!isDay`: clear sky → `MOON`, partly cloudy → `CLOUD_MOON`, rain/drizzle → `MOON_RAIN`, snow → `MOON_SNOW`, thunder → `MOON_THUNDER`. Night precipitation glyphs composite a small crescent moon in the upper-left with a shifted cloud and precipitation elements. `drawMoon` uses `PathOperation.Difference` to subtract a shadow circle from the outer circle, producing a clean crescent without the EvenOdd overflow artifact. `drawBolt` is a shared private helper used by both `THUNDER` and `MOON_THUNDER`.

**Section labels:** 11 sp uppercase with `letterSpacing = 0.8.sp` — keep this style consistent across any new sections.

**`CurrentHeader` element order:** location (12 sp, Medium, 2 sp letter-spacing, uppercase) → glyph + condition (Row, 20 dp glyph, 15 sp Normal) → temperature (96 sp, Thin — the undisputed hero) → H/L → feels-like → lookahead pill. The large standalone glyph (76 dp) no longer appears in the hero. The location `Text` needs explicit `textAlign = TextAlign.Center` + `Modifier.fillMaxWidth()` — without it, a name that wraps to two lines (e.g. "Franklin Park, New Jersey") left-justifies its second line inside an auto-sized text box, which reads as the whole block being left-aligned even though the box itself is centered in the parent `Column`.

**Hero text color (`heroTextColors` / `heroBackdropIsDark`, both in `WeatherBackground.kt`/`WeatherComponents.kt`):** `CurrentHeader` and the "sky\|speak" wordmark no longer take the fixed app-wide `TextPrimary`/`TextSecondary` directly — they sit with no card or scrim behind them, directly on `WeatherBackground`'s per-condition scene, so a color calibrated for the app's cream/white card surfaces doesn't reliably hold contrast against every possible sky. `WeatherScreen.kt`'s `WeatherContent` computes `heroBackdropIsDark(code, isDay, alerts)` once and passes the result into `heroTextColors(heroBackdropIsDark)` to get the `(primary, secondary)` pair used by both. Dark theme is unaffected (returns the ordinary `TextPrimary`/`TextSecondary` — dark theme's own sky stops are already recalibrated dark enough, see `conditionGradient`'s doc comment). In light theme: a dark backdrop flips to a light-on-dark pair borrowed verbatim from `DarkColors.onBackground`/`onSurfaceVariant` (`0xFFE0E6ED`/`0xFF8A9BAD`); everything else keeps `TextPrimary` but swaps the secondary tone for `0xFF3F5670` — the same slate-blue ink `tipColors()`'s RAIN tone and `drawRain`'s light-mode ink already use — rather than inventing a new color.

`heroBackdropIsDark()` deliberately mirrors `conditionGradient`'s own `sky` branch order/ranges (`code in 95..99` thunder / `71..86` snow / `51..82` rain / `45..48` fog / `!isDay` / else), rather than reusing `classify()`'s `Scene` — an earlier version did reuse `classify()`, and it was wrong: `classify()`'s codes-2-3 (Overcast/Cloudy) branch doesn't check `isDay` at all (it picks Overcast/MostlyCloudy/PartlyCloudy from `cloudCoverPct` alone), but `conditionGradient`'s `sky` selection *does* fall through to a dark navy `!isDay` branch for those same codes, since Overcast isn't one of the four explicit precip/fog ranges checked first — so night+Overcast painted a dark backdrop that the Scene-based check missed entirely. Found two ways: first at Franklin Park, NJ in daylight (Overcast — `TextSecondary` measured ~2.2:1 against the flat gray wash, well under WCAG's 4.5:1 floor) and again at the same location at night (Overcast still, but now `conditionGradient` paints it dark navy — `TextPrimary` measured only ~2.3:1 there, the daytime fix having assumed a light backdrop). Both fixed by the same mechanism, contrast now ~4.3–5.6:1 for light backdrops and ~4.3–4.7:1+ for dark ones. Tornado/Hurricane are handled separately via `alerts` (not `code`), since `conditionGradient` has no alert awareness — `WeatherBackground` layers its own dark overlay rect for those scenes independent of the base gradient.

**Hero font weight (`heroWeight` in `WeatherComponents.kt`):** A second, related light-theme-only issue, user-reported by direct comparison with dark mode: even with `heroTextColors` fixing contrast, the hero's already-light weights (`Thin` display numeral, `Light` wordmark, `Normal` body text) read as visually "weak" in light theme specifically — a real optical effect (irradiation: a bright surround makes a dark glyph look thinner than the identical glyph reversed light-on-dark), not a rendering bug, so dark theme's light-on-dark hero text at the same nominal weights reads fine. `heroWeight(base: FontWeight)` steps every hero text weight up one level (`Thin→ExtraLight`, `Light→Normal`, `Normal→Medium`, `Medium→SemiBold`) in light theme only, returning `base` unchanged in dark theme. Applied to every `Text` in `CurrentHeader` (location, condition, temperature, H/L, feels-like, lookahead pill) and the "sky\|speak" wordmark in `WeatherScreen.kt` — the same set of elements `heroTextColors` covers, since both fixes address the same hero-vs-background legibility concern. Verified on-device: light-mode hero at Franklin Township, NJ visibly reads heavier after the change (before/after screenshots), dark mode confirmed pixel-identical in weight (unchanged code path).

**Lookahead pill (`WeatherData.headline`):** `WeatherData.headline` is `String?` — populated by `WeatherRepository.buildUpcomingHeadline()` when hourly data is present, null otherwise. `buildUpcomingHeadline()` itself always returns a non-null `String`. `CurrentHeader` falls back to `data.comparedToYesterday` when `headline` is null. Operates on the raw `HourlyBlock` + `nowIndex` (the exact position of the current hour in the full 7-day API array) so the scan always starts from the true "now" and naturally crosses into the next day. Scans the next 12 raw hourly entries (`nowIndex+1` .. `nowIndex+12`) for the first significant condition change — Thunderstorm, Snow, Rain, Freezing rain, Drizzle, Fog — relative to the current WMO code. Appends a wind note when the next-12-hour max exceeds 40 km/h / 25 mph. Trusts WMO codes directly; only light drizzle (51–57) requires a ≥30% precipitation-probability floor. Falls back to a dominant-condition summary over the next 6 hours (rather than `null`) when no significant change is detected — but only asserts a specific condition (e.g. "Clear skies for the next few hours") when one WMO code holds a real majority (≥60%) of those 6 hours; otherwise returns "Mixed conditions over the next few hours." rather than guessing off a bare plurality.

**`TipBanner` source data:** Tips are generated by `WeatherRepository.buildTips()`. At night (`isDay = 0`) the tip day switches to the next daily entry so tips reflect upcoming conditions rather than the day just passed. The precipitation probability passed to `buildTips` is always `max(tipDay.precipProbMax, maxPrecipChanceInNext12Hours)` to capture short-range rain even when the daily summary hasn't rolled over yet.

**Daily forecast precipitation probability:** Shown inline below the WMO glyph in `DailyCard` rows, using the same `Indigo` style as the hourly row, whenever `precipProbMax > 0` and the day's WMO code is in the precipitation/fog range (45–99).

**`DailyCard`'s temperature range bar (`TempRangeBar`):** A `Canvas`-drawn horizontal bar per day, positioned between the low and high temperature labels — the filled segment spans `weekMinC`–`weekMaxC` proportionally and is colored via `tempColor()`, a 6-stop cool-to-warm gradient. `DailyCard` derives `val metric = data.windUnit == "km/h"` (rather than adding a new `WeatherData` field, since `windUnit` already reliably encodes the unit system) and passes it through to `TempRangeBar`, which converts `low`/`high` to true Celsius via `toCelsius()` before calling `tempColor()` — see the Key invariants entry on unit-ambiguous "C"-suffixed fields.

**`AttributionFooter` (`ui/components/WeatherComponents.kt`):** Shows the Open-Meteo CC BY 4.0 attribution line, plus a tappable "☕ Support the developer" line beneath it in `MaterialTheme.colorScheme.primary` that opens a donation page via `LocalUriHandler.current.openUri(...)`. This was the first use of `LocalUriHandler` in the codebase. The destination URL lives only in this composable's source — do not duplicate it in documentation or comments elsewhere.

## Key invariants

- `WeatherData` fields store values **in the user's current unit system** (not always metric). This is set at fetch time via `UnitSystem.apiTemp`/`apiWind`/`apiPrecip` passed to Open-Meteo, and the unit labels (`windUnit`, `precipUnit`, `visibilityUnit`, `tempLabel`) travel alongside.
- The 30-minute cache in `WeatherRepository` is in-memory only and scoped to the process. Widget updates bypass the app's ViewModel and create their own `WeatherRepository` instance.
- OpenRouter key resolution: `PreferencesStore.getOpenRouterKey(buildDefault)` returns the on-device key first, falling back to the build-time `BuildConfig` value. Always pass `BuildConfig.OPENROUTER_API_KEY` as the fallback.
- Drawable resource names must be all-lowercase (`a-z`, `0-9`, `_`) — Android's AAPT2 rejects uppercase characters.
- `MetricChart.dayChangeIndex` must be derived from `d.hourLabels.indexOfFirst { it == "12 AM" }.takeIf { it >= 0 }` in `buildMetricTiles` and passed to every `MetricChart` constructor — do not hardcode or omit it.
- `parseTimeHour` handles both 24-hour (`"18:30"`) and 12-hour AM/PM (`"6:30 PM"`) formats. Always use it when parsing sunrise/sunset strings from `WeatherData` inside a `DrawScope` or Canvas block.
- Any threshold logic keyed off a `WeatherData`/`DayEntry` "C"-suffixed field (e.g. `tempColor()` in `DailyCard`'s temperature range bar) must convert to true Celsius first via a helper like `toCelsius(v, metric)` (mirrors `WeatherAdvisor.toC`) — the field only *sounds* like it's always Celsius. Skipping this previously made the 7-day forecast bar render a uniformly hotter (reddish) color in °F than the identical real temperatures showed in °C, since raw Fahrenheit numbers are always larger.
- **Snowfall is never in `precipUnit`.** Verified live against Open-Meteo: `precipitation_unit=mm` (this app's METRIC setting) leaves `snowfall`/`snowfall_sum` in **cm** — a real 10x unit mismatch, not just a cosmetic label difference. Only `precipitation_unit=inch` (IMPERIAL) converges snowfall to `"inch"` too, matching `precipUnit`. Always pair a snow amount (`WeatherData.currentSnowfall`, `hourlySnowfall`, `DayEntry.snowfallSum`) with `WeatherData.snowUnit` (`UnitSystem.snowLabel`: `"cm"` metric / `"in"` imperial) — never `precipUnit`.
- `WeatherData.precipMm` (current-hour total) and `currentRainMm`/`ChatRepository`'s "rain:" line are **rain+showers only**, not the same figure — `precipMm` is Open-Meteo's `precipitation`, which bundles rain+showers+snow water-equivalent together, so it alone can't tell a caller whether it's actually raining or snowing. Anything that needs to know the *type* (metric tile, chat context, `WeatherAdvisor`) must read `currentSnowfall`/`currentRainMm`/`hourlySnowfall`/`hourlyPrecipAmount` instead, never infer type from `precipMm` or from `precipChance`/`precipProbMax` (both are `precipitation_probability`, which doesn't distinguish rain from snow at all — a high reading only means "some precipitation is likely," and treating it as "rain" was a real bug in `WeatherAdvisor.umbrella()` that told people to grab an umbrella on snow days; fixed via the `Ctx.isSnowy` check, computed from real `currentSnowfall`/`hourlySnowfall` data with an `isSnowOrIce(code)` fallback).
