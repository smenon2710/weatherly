# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

SkySpeak: Premium Weather Chat is an Android weather app (Kotlin + Jetpack Compose) that pulls forecast data from Open-Meteo (no API key) and optionally uses OpenRouter for an AI chat assistant. The app was formerly named Weatherly. The Play Store `applicationId` is `io.github.smenon2710.skyspeak`, but the Kotlin `namespace`, package (`com.example.weatherly`), and all `Weatherly`-prefixed class names are intentionally left unchanged — Google Play only requires `applicationId` to be unique, not the internal package name, so this was a low-risk one-line change rather than a full source-tree rename.

## Build & run

Open the project root in Android Studio (Quail or newer) and let Gradle sync, then run on a device or emulator via the IDE's run configuration. This is the primary, intended workflow.

**There is no `gradlew`/Gradle wrapper checked into this repo** — don't assume `./gradlew <task>` works; it won't, the file isn't there. If you need to drive a build from the command line (CI, an agent without IDE access, etc.), Android Studio has already cached the exact Gradle distribution `gradle/wrapper/gradle-wrapper.properties` asks for under `~/.gradle/wrapper/dists/`, and Android Studio bundles its own JBR — both are usable directly without installing anything system-wide:

```bash
export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"   # macOS path; adjust per OS
GRADLE_BIN=$(find ~/.gradle/wrapper/dists -path "*gradle-*-bin/*/gradle-*/bin/gradle" | head -1)
"$GRADLE_BIN" assembleDebug     # debug APK
"$GRADLE_BIN" bundleRelease     # signed release AAB (needs STORE_PASSWORD/KEY_PASSWORD in local.properties)
"$GRADLE_BIN" test              # unit tests (none yet; placeholder)
"$GRADLE_BIN" lint
```

This is exactly how the versionCode 9 release AAB was built and verified (`jarsigner -verify`, then a real sanity-install via `adb`) without ever opening Android Studio — see the Play Store launch status note below and the Launch Checklist in `PLAYSTORE_LAUNCH.md`.

## API key setup

Copy `local.properties.template` to `local.properties` (already git-ignored) and fill in:

```
sdk.dir=/path/to/your/Android/sdk
OPENROUTER_API_KEY=sk-or-...   # optional — quick-suggest chips work without it
OPENROUTER_MODEL=openrouter/free   # optional override; any OpenRouter model ID works
```

Both values are injected at build time into `BuildConfig.OPENROUTER_API_KEY` and `BuildConfig.OPENROUTER_MODEL`. If no key is present at build time, users can enter one directly in the chat screen; it is stored in `SharedPreferences` via `PreferencesStore`.

## Architecture

**Single-activity, three-screen app.** `MainActivity` holds a `WeatherViewModel` (activity-scoped) and dispatches between `WeatherScreen`, `ChatScreen`, and `SettingsScreen` via `AnimatedContent` keyed on a private `Screen` enum (`WEATHER`, `CHAT`, `SETTINGS`). `WeatherViewModel` exposes `themePreference: StateFlow<ThemePreference>` (read at the `MainActivity` root to pick light/dark/system for `WeatherlyTheme`) so `SettingsScreen` can change it. `SettingsScreen`/`SettingsViewModel` also own unit-system switching, on-device OpenRouter key/model management (the key field is write-only — `SettingsViewModel` never echoes the stored secret back), widget background transparency, haptic feedback on/off (see "Haptic feedback" below), and a "Rate on Google Play" deep link with a browser fallback.
(A fourth screen, `RadarScreen` — a RainViewer/OSMDroid precipitation map — existed briefly but was removed as low-value; see git history if reviving it. Its `osmdroid` dependency, `ACCESS_NETWORK_STATE` permission, and the `@JsonClass`-wide ProGuard rule it required are gone with it.)

**Data layer:**

| Class | Role |
|---|---|
| `NetworkModule` | Singleton object wiring six Retrofit clients: Open-Meteo forecast, Open-Meteo geocoding, Open-Meteo air quality, OpenRouter, NWS (`api.weather.gov`, for active weather alerts), and NOAA CO-OPS (`api.tidesandcurrents.noaa.gov`, for tide predictions — see "Tides" below). Exposes `makeStreamingCall(Request)` for raw SSE calls. No DI framework. HTTP logging is added via the `OkHttpClient.Builder.addDebugLogging()` extension, which has two implementations in build-type-specific source sets — `src/debug/java/.../DebugLogging.kt` (adds `HttpLoggingInterceptor`) and `src/release/java/.../DebugLogging.kt` (no-op). This is required, not just cosmetic: `logging-interceptor` is a `debugImplementation` dependency, so a runtime `if (BuildConfig.DEBUG)` guard alone would still fail to *compile* in release (the import wouldn't resolve on that classpath). The NWS client carries its own OkHttp interceptor setting a `User-Agent`/`Accept` header — NWS throttles requests without a real identifying `User-Agent`. |
| `WeatherRepository` | Single source of truth. Fetches forecast + air quality + NWS alerts + tide predictions in parallel (`coroutineScope`/`async`). The alerts and tide fetches are both wrapped in `runCatching { }.getOrNull()` — NWS is US-only and has no key of its own, and NOAA tide coverage is gated to begin with (see "Tides" below) — so a failure or an out-of-coverage point (empty `features` array, or `TideStations.nearest()` returning null) must never fail the overall weather fetch. 30-minute in-memory cache keyed by `"lat,lon,units"` covers `WeatherData.alerts`/`tides` too, no separate cache. See "Weather alerts" below for the mapping/severity-inference details. Also requests Open-Meteo's `rain`/`showers`/`snowfall` fields (current, hourly, daily) separately from the generic `precipitation`/`precipitation_probability` fields, so callers can tell rain from snow using real data instead of guessing from the WMO code — see the snowfall-unit and precip-type entries in Key invariants. `buildDayOutlookTips()` computes practical per-day advice (see "Daily forecast tips" below) for every entry in `daily`, independent from `buildTips()`'s existing "today"-phrased hero `TipBanner` tips. The forecast fetch (`api.getForecast`) is retried up to 2 more times (3 attempts total, 1s/2s backoff) on a transient failure — a real 5xx, or a malformed/non-JSON body surfacing as a Moshi `JsonEncodingException`, which is an `IOException` under the hood — since a failure here fails the whole screen; the other three fetches stay single-attempt behind their own `runCatching{}.getOrNull()`. **`getWeather()`'s catch block must rethrow `CancellationException` before its general `catch (e: Exception)`** — versionCode 15 fixed a real bug where a normal, expected cancellation (a fetch superseded by a newer one, or torn down with the screen) was being caught, logged, and reported to the user as a fake "Couldn't connect" network error; found by adding exception logging (`Log.w`, survives release builds — nothing in `proguard-rules.pro` strips `Log` calls) after a real user report, confirmed live via a captured `JobCancellationException` reaching that catch block. `ChatViewModel` already had the correct guard for this same class of bug; `WeatherRepository` didn't. Any remaining real failure is mapped to a friendly message (`friendlyMessage()`) rather than showing the raw exception text — same principle as `ChatRepository.httpMessage()`. |
| `ChatRepository` | Streams OpenRouter responses token-by-token via SSE (`askStreaming`) and simulates the same feel for rule-based answers (`simulateStreaming`). Both return `Flow<String>`. Retries once on HTTP 429. All requests include `HTTP-Referer` and `X-Title` headers for OpenRouter log attribution. `systemPrompt()`'s `weatherBrief()` prepends any active NWS alerts (event, severity, expiry) to the WEATHER DATA block, and the rules explicitly tell the model to weigh them and volunteer them even when not asked directly (e.g. mention a Winter Weather Advisory on a driving question). `weatherBrief()` reports rain and snow separately (e.g. `"snowing: 1.2 cm"`, `"(2.1 cm snow)"` next to an hour/day) rather than one type-agnostic `precip` figure, and the system prompt explicitly tells the model a `"% precip"` reading alone doesn't imply rain. `systemPrompt()` also carries three guardrail rules (topic scope, safety/liability tone, untrusted-data awareness) — see "AI chat: local-first routing, guardrails, and usage cap" below. |
| `ForecastCache` | Persists the last successful `WeatherData` as JSON in `SharedPreferences` (`forecast_cache`). `WeatherViewModel.init` loads it synchronously so the app opens instantly offline. Replaced by fresh data on every successful network fetch. |
| `PreferencesStore` | `SharedPreferences` wrapper for unit system, saved places, selected place, on-device OpenRouter key/model, the tracked-alert list used for resolution detection (see "Alert resolution tracking" below), the daily LLM usage counter (see "AI chat: local-first routing, guardrails, and usage cap" below), widget transparency, and the haptic feedback on/off toggle (see "Haptic feedback" below). |
| `WeatherAdvisor` | Pure object (no network). Answers six hard-coded intents (UMBRELLA, JACKET, WALKING, DRIVING, HIKING, CLOTHING) locally from the current `WeatherData`. `Ctx.isSnowy` (real `currentSnowfall`/`hourlySnowfall` data, falling back to `isSnowOrIce(code)`) is checked before any rain-percentage logic in every intent — `umbrella()` used to recommend an umbrella on snow days because its rain-percentage branch fired off `precipitation_probability` alone, which doesn't distinguish rain from snow. `matchIntent(text): AdviceIntent?` classifies free-form chat text against the same six intents for local-first chat routing — see "AI chat" below. |
| `MoonCalculator` (`util/`) | Pure object. Computes lunar phase from Julian date arithmetic (reference JD 2451550.260, synodic month 29.530588853 days). Exposes `phase(y,m,d): Double` (0=new, 0.5=full), `phaseName(phase)`, `illuminationPct(phase)`, and `nextEvent(phase): Pair<String,Int>` (label + days). |
| `TideStations` (`util/`) | The "is this location coastal" gate — see "Tides" below for the full rationale, including the known limitation (deep tidal rivers can resolve closer than genuine coastal towns, so this isn't a perfect coastal classifier). `nearest(context, lat, lon, maxKm = 10.0)` does a plain linear haversine scan (negligible cost, ~3500 stations) against the bundled `assets/tide_stations.json`, returning the closest station or null. |

**UI layer:**

- `WeatherViewModel` — `AndroidViewModel` exposing `StateFlow<WeatherUiState>`. On `init`, loads `ForecastCache` synchronously so the screen is never blank on cold start. Handles location resolution (falls back to `LocationProvider` when no place is selected), unit switching, city search, and pull-to-refresh. `WeatherUiState.Success` carries a `cachedAt: Long?` timestamp; non-null means the data came from cache and triggers a "Showing data from Xm ago" label. Background refreshes keep existing data visible (only the spinner changes).
- `WeatherScreen`'s location-permission `rememberLauncherForActivityResult` callback calls `viewModel.load(background = state is WeatherUiState.Success)` rather than an unconditional cold load. The `LaunchedEffect(Unit)` that triggers the permission request re-fires every time `WeatherScreen` re-enters composition (cold start, and every return from Chat/Settings since `AnimatedContent` disposes/recomposes the screen). Since the permission is normally already granted, the callback fires almost immediately — a cold load there would flash existing on-screen content back to a full `Loading` state before the refetch completes. This mirrors the `ON_RESUME` effect's existing `if (state is WeatherUiState.Success)` guard.
- `ChatViewModel` — Exposes `messages`, `sending`, and `streamingText: StateFlow<String>`. Accumulates SSE/simulated chunks into `_streamingText`; on completion moves the full text into `_messages`. `clear()` cancels any in-flight stream job. `hasKey: Boolean` is a `get()` property that returns true when an API key is available (on-device or build-time). `send()` does local-first routing and usage-cap gating before ever calling the LLM — see "AI chat" below. `sendLocal(intent, question, weather, units)` is the single source of truth for "answer via `WeatherAdvisor` instead of the LLM" (including the "open the weather screen first" fallback when `weather == null`), shared by `send()`'s routing and `ChatScreen`'s suggestion-chip taps — `addLocalExchange(question, answer)` remains the lower-level primitive both `sendLocal()` and the usage-cap redirect message call directly.
- `ChatScreen` empty state — when `messages.isEmpty()`, shows three tappable example query rows (each calls `onQueryClick` to populate the input field). When `chatViewModel.hasKey` is false, appends a subdued "Tip: add your OpenRouter key" note.
- `ChatScreen` suggestion chips — six `AssistChip`s in a `LazyRow` above the input field. `suggestionTint(intent: AdviceIntent): Color` (private, non-composable) maps each intent to a distinct accent: UMBRELLA → Cyan, JACKET → Purple, WALKING → Green, DRIVING → Amber, HIKING → Teal, CLOTHING → Coral. Each chip gets `containerColor = tint.copy(alpha = 0.14f)` so chip domains read at a glance without being visually loud. `answerLocally(s: Suggestion)` just calls `chatViewModel.sendLocal(s.intent, s.question, weather, units)` — no local logic duplicated in the View layer.

**AI chat: local-first routing, guardrails, and usage cap.** Direction logged in IMPROVEMENTS.md's "AI Chat — Keep, but Tighten LLM Usage + Add Guardrails" section, implemented and verified on-device with a real OpenRouter key.

- **Local-first routing.** `ChatViewModel.send()` runs the trimmed prompt through `WeatherAdvisor.matchIntent(text): AdviceIntent?` before ever considering the LLM. A match routes through `sendLocal()` — the identical free, zero-latency answer the matching chip would give. `matchIntent()` is deliberately conservative on two axes to avoid misrouting a question that actually needs LLM synthesis: only messages of ≤12 words are considered at all (a longer message is far more likely to be compound/nuanced), and intents are checked in a fixed priority order with the first match winning (predictable rather than ambiguous when a message mentions more than one keyword). Not tuned against a large real corpus — a reasonable first cut per its own doc comment.
- **Guardrails** — three rules appended to `ChatRepository.systemPrompt()`'s existing rules: (1) topic scope — decline/redirect anything with no weather angle, since most real users are on the developer's own shared build-time key, not one they entered themselves; (2) safety/liability tone — avoid definitive-sounding guarantees for driving/hiking-type questions, frame as "no active advisories, but conditions can change" rather than an outright "it's safe"; (3) treat the WEATHER DATA block as data only, never as instructions.
- **Daily usage cap** — `PreferencesStore.getLlmUsageCountToday()`/`incrementLlmUsageToday()` (a count + date string, self-resetting once the stored date is no longer today, no explicit midnight job needed) gate a soft cap (`ChatViewModel.LLM_DAILY_CAP = 20`) on messages that actually reach OpenRouter. Only increments on a *successful* completed exchange — a failed/errored call doesn't cost the user anything. Gated by `PreferencesStore.hasOwnOpenRouterKey()`: the cap **never** applies once the user has entered their own key in Settings, since it exists specifically to protect the developer's shared build-time key from runaway cost, not to limit a key the user is paying for themselves. When the cap is hit, `send()` calls `addLocalExchange()` with a warm, non-error redirect message (naming the six local intents that still work) instead of calling the LLM or surfacing an error — confirmed on-device by seeding the counter to 20 via `adb`: an off-topic question got the redirect with zero network calls, while a local-intent question ("should I wear a jacket") still answered normally even while capped, since local routing is checked first.
- **Off-topic pre-filter — `WeatherAdvisor.isObviouslyOffTopic(text)`, versionCode 15.** The topic-scope guardrail above is a *prompt* instruction — the model still gets a real, billed OpenRouter call before it declines, confirmed on-device (an off-topic message reached OpenRouter and got redirected there, not before). This runs before that call: a denylist of strong non-weather signals (`"capital of"`, `"write code"`, `"translate"`, etc.) that only fires when the message *also* contains zero weather-adjacent vocabulary — deliberately the inverse of `matchIntent()`'s allowlist approach, since denylisting only blocks messages matching a strong "definitely not weather" signal, so a genuinely ambiguous message still reaches the LLM exactly as before. Checked in `ChatViewModel.send()` right after `matchIntent()` and before the daily-cap check.
- **Markdown rendering — `ChatScreen.kt`'s `renderChatText()`, versionCode 15.** The system prompt asks the model not to use markdown, but general-purpose models don't reliably follow that — user-reported literal `**bold**` asterisks showing in bubbles even with the rule in place. `MessageBubble`/`StreamingBubble` never had any formatting layer at all (`Text(text = msg.text)` verbatim), so this is real client-side enforcement, not just a prompt nudge: a minimal single-pass parser handling `**bold**` only, via `buildAnnotatedString`. Streaming-safe: an unclosed `**` (the closing pair hasn't arrived yet) is left as literal text rather than swallowed, so nothing is eaten mid-stream — it just briefly shows raw asterisks until the closing pair streams in, then converts.
- **OpenRouter model-override gating — `PreferencesStore.getEffectiveOpenRouterModel()`, versionCode 15.** Real gap found and fixed: `ChatViewModel`'s `model` getter read the stored model override unconditionally, with no check on whether the user had entered their own key — so any user, on the shared build-time key, could type a paid or `auto`-routing model ID into Settings and have every call bill against the developer's key. `getEffectiveOpenRouterModel()` only honors the stored override when `hasOwnOpenRouterKey()` is true, else forces `BuildConfig.OPENROUTER_MODEL` regardless of what's saved — enforced at this single resolution point so no caller can forget the check. `SettingsScreen`'s model field is now `enabled = hasOwnKey` (disabled until a key is saved) as the first line of defense, with the resolution-point gate as the real enforcement behind it. Two-step UX by design: saving a key and a custom model in one sitting takes two taps (save key → field unlocks → edit model → save again), since the field can't be edited before `hasOwnKey` flips true.
- `WeatherScreen` / `ChatScreen` / `SettingsScreen` — Compose screens consuming the ViewModel via `collectAsStateWithLifecycle`.
- `ui/components/` — Reusable Compose functions (header, hourly row, daily list, metric tiles, detail sheets, `WeatherBackground`).
- `ui/theme/` — Material 3 color scheme, typography, `WeatherlyTheme`.

**`WeatherBackground` (`ui/components/WeatherBackground.kt`):** Full-screen animated backdrop behind the entire scrolling `WeatherScreen` content (not just the hero) — an Apple-Weather-style per-condition scene, replacing the old hero-only static gradient. A private `Scene` enum (26 values, covering Clear/Cloud, Liquid Precip, Frozen Precip, Atmospheric Obscurations, and Convective/Severe categories) is chosen by `classify()` from real data only, never decoration for its own sake:

- WMO `code` (extended beyond the coarser ranges `WeatherRepository`/`WeatherAdvisor` use, to also split out freezing rain/drizzle (`56/57/66/67`), snow grains as sleet (`77`), and thunderstorm-with-hail (`96/99`) from plain thunderstorm (`95`)).
- `cloudCoverPct` splits WMO's single "overcast" bucket into `MOSTLY_CLOUDY` (65–89%) vs `OVERCAST` (≥90%) — a distinction the 4-value WMO code alone can't express.
- `visibility` (unit-aware — converts mi→km before comparing, since a raw-mile reading against a km threshold would mislabel every imperial user's fog) splits `MIST` from `FOG` at the standard ~1 km meteorological threshold; missing visibility data defaults to `FOG` (the denser reading), not `MIST`.
- `aqi` still tints `FOG` warmer/browner toward "smoky" past 100 (no separate smoke WMO code exists), and now also independently triggers `HAZE` on an otherwise clear/cloudy day (no fog code required) once `aqi > 100`.
- `TORNADO` and `HURRICANE` have no WMO forecast code at all — `classify()` instead checks active `WeatherData.alerts` for NWS `event` text containing "Tornado" / "Hurricane" / "Tropical Storm", which is real signal NWS actually issues, checked first (overrides every other input, most severe wins).
- `DUST_STORM` and `VOLCANIC_ASH` are a deliberate exception: no code, no alert type, no other signal Open-Meteo or NWS provides for either, so `classify()` never returns them — they're implemented (own enum value, own `drawDustStorm`/`drawAsh` renderer) but genuinely unreachable today, per an explicit product decision to have the visuals ready ahead of a future data source rather than fake a trigger.
- A separate `severeWind` boolean (real `windKmh`/`windGustKmh`, ≥45 km/h gust) layers `drawWindStreaks` on top of *any* scene except Tornado/Hurricane (which already imply extreme wind) — this is what makes `SNOW_HEAVY` + high wind read as a blizzard, without a dedicated `BLIZZARD` scene.

One shared `timeMs` clock (`withFrameMillis` in a `LaunchedEffect` loop) drives every particle; positions are pure functions of `(timeMs, per-particle seed)` computed inside a single `Canvas`'s draw phase, not composition — reading `timeMs` only there means each tick redraws just that Canvas, not the whole screen. Per-particle seed lists (`Seed(a,b,c,d): four random floats`) are generated once per scene via `remember(scene)`, never regenerated per frame, so particles don't jitter. Renderers, each reused across multiple scenes rather than one bespoke illustration per scene: `drawRain` (angled streaks, `RainIntensity` tiers: DRIZZLE/LIGHT/MODERATE/HEAVY), `drawHurricaneRain` (near-horizontal sheets, a distinct function rather than a rain-intensity tier so normal rain can't accidentally inherit hurricane-grade slant), `drawSnow` (`SnowIntensity` tiers, sinusoidal side-sway), `drawSleet` (fast slanted streaks + static bounce-tick marks), `drawHail` (falling spheres + static impact marks), `drawFogBands` (drifting translucent bands, shared by `MIST`/`FOG`/`DUST_STORM`), `drawHaze` (mostly-static warm horizon wash — deliberately not drifting like fog, since haze is a stagnant-air tint), `drawClouds` (drifting 3-circle silhouettes; `OVERCAST` instead draws one flat full-canvas gray rect, not more cloud blobs, per the "texture-blocked sheet, no shadows" brief), `drawStars`, `drawSunGlow`, `drawMotes` (golden-hour-only "beautiful evening" extra layer), `drawThunderFlash`, `drawGroundWash` (a bottom-of-screen translucent strip standing in for wet/snowy/icy ground — used by `RAIN_HEAVY`, `SNOW_MODERATE`/`HEAVY`, `SLEET`), `drawIceSheen` (a moving specular highlight for freezing rain's "high-gloss" look, distinct from the flat-alpha ground wash), `drawAsh` (a darker/faster/smaller cousin of `drawSnow`), `drawTornado` (the one genuinely bespoke shape: stacked wobbling ellipses tapering to a point, rotating via a `timeMs`-driven angle, plus orbiting debris dots), `drawWindStreaks`. The base gradient is `conditionGradient` (unchanged) stretched to the full screen rather than just the hero height.

**Particle color, not just alpha, must be theme-aware.** `drawRain`/`drawHurricaneRain`/`drawSnow`/`drawSleet`/`drawHail`/`drawIceSheen`/`drawWindStreaks` all take an `ink: Color` param computed once in `WeatherBackground` (`rainInk`, `snowInk`, `sleetInk`, `hailInk`, `windInk`, `iceSheenInk`, `snowWashInk`) rather than hardcoding `Color.White`. Dark mode keeps white — it pops against the dark gradient stops. Light mode uses the app's existing rain/snow "slate blue" tip-tone family (see `tipColors()`) instead, e.g. `rainInk = Color(0xFF3F5670)` — **lowering alpha alone cannot fix this**, since white-on-pale-pastel is a wrong hue, not just a wrong opacity, and was invisible enough in practice that the whole animated background read as "not changing with the weather" in light mode even though `Scene`/the base gradient were both classifying and shifting correctly the whole time (confirmed via a real device screenshot during testing). `drawStars` and `drawThunderFlash` are the only two renderers that keep plain `Color.White` unconditionally — correctly, since stars only render at night (when `conditionGradient`'s stop is dark navy in *both* app themes) and a lightning flash is inherently a white light burst regardless of theme.

Cards (`GlassCard`) stay fully opaque over this background — a translucent "frosted glass" card fill (`LocalTranslucentCards`, alpha-blending `surface` at ~0.72–0.78) was tried and reverted. Real glassmorphism needs actual blur (`RenderEffect`, API 31+ only), not just alpha; alpha-blending a near-white light-mode fill over this busy animated background instead produced a visibly patchy card with seams at the rounded corners — worse in light mode (dark-on-dark blends forgivingly against a dark scene; light-on-colored doesn't) — confirmed via a real device screenshot during testing. `WeatherBackground` still shows through in the hero and in the gaps/margins around cards; cards themselves are solid, matching every other screen.

**Weather alerts (`WeatherAlert` / `AlertSeverity` in `data/model/WeatherData.kt`):** Official advisories from the National Weather Service (`api.weather.gov/alerts/active?point=lat,lon`), US coverage only, free, no key. `WeatherRepository.mapAlerts()` builds the domain list from the raw `NwsAlertsResponse`:

- Filters to `status == "Actual"` (excludes Test/Exercise/Draft products NWS also publishes through this feed), dedups by `id`.
- **Same-event/same-area collapse:** NWS can independently issue multiple non-linked products for the identical event and area — confirmed live for Franklin Park, NJ: two separate Air Quality Alert issuances covering the exact same 3 UGC zones simultaneously, a day apart, neither referencing the other (`references: []`, `messageType: "Alert"` not `"Update"`). This is a rolling day-ahead reissuance pattern (each ~30hr window overlapping the previous one), not an error, but showing both raw CAP products reads as a duplicate — NWS's own consumer-facing tools show only the current one. `mapAlerts()` groups by `(event, areaDesc)` (falling back to that alert's own `id` when either is null, so incomplete-data alerts never accidentally collapse into each other) and keeps only the most-recently-`sent` entry per group, via `parseInstantOrMin()` (the `Instant.MIN`-default counterpart to `parseInstantOrMax()`, so a missing `sent` value loses rather than wins the comparison).
- **Severity inference:** NWS tags nearly every Air Quality Alert `severity: "Unknown"` — its CAP severity taxonomy has no air-quality category. `parseSeverity()` falls back to parsing the description for EPA's standardized "Code Red/Orange/Purple/Maroon" AQI names (the literal terms every state environmental agency uses nationwide for these alerts) when `event` contains "Air Quality" and CAP severity is absent, defaulting to `MODERATE` (never the calmest tier) if no code keyword matches. Without this, a "Code Red...unhealthful for the general population" alert would render in the same visual tier as a Small Craft Advisory.
- **Sort order:** primarily by severity (most severe first), with effective-time as a tiebreaker — NWS can have multiple same-severity products active simultaneously (e.g. an Air Quality Alert for today and a separate one for tomorrow), so ordering would otherwise depend on arbitrary API array order.
- **`ends` vs `expires`:** `expiresLabel` prefers `p.ends` (when the hazard itself is expected to end) over `p.expires` (when the CAP *message* expires, which for long-duration products like a multi-day Flood Watch is often much sooner than the actual hazard window and reads as misleadingly early). Falls back to `expires` for shorter products that don't set `ends`.
- **`formatNwsTime()` includes day context**, not just clock time (e.g. `"Tomorrow, 8:00 PM"` / `"Jul 18, 8:00 PM"`, plain `"8:00 PM"` only for today) — NWS legitimately issues multiple alerts sharing an identical event name for one point (day-by-day reissuance without linking via `references`, or overlapping zone coverage for border locations; confirmed live for Franklin Park, NJ, which had 3 simultaneously-active "Air Quality Alert" entries with distinct IDs). Time-only formatting made two such alerts effective/expiring at the same clock time on different days render as literally identical text.
- **Text normalization:** `normalizeNwsText()` collapses NWS's hard-wrapped-at-80-columns literal newlines into spaces (preserving genuine blank-line paragraph breaks) — rendered verbatim, `description`/`instruction` would show as choppy short lines instead of normal paragraph reflow.
- `WeatherData.alerts: List<WeatherAlert> = emptyList()` — the default is required, not cosmetic: `ForecastCache` deserializes old cached JSON (written before this field existed) via Moshi's reflective adapter, which only fills a missing key from a constructor default.

UI: `AlertBannerList` (`ui/components/WeatherComponents.kt`) is a single-line severity strip, not a `GlassCard` — left 4dp accent bar + subtle tint in the alert's severity color, the same left-accent-bar language `TipBanner` already established elsewhere in the app, rounded only on the right corners. This replaced an earlier full-card treatment (icon + bold title + subtitle + chevron, four lines tall) after user-reported testing found it took over too much of the screen with multiple active alerts, on top of the `DetailSheet.AlertList` cropping bug below. Two *earlier* revisions had already tried to make the card visually exceptional (full-bleed/square to read as a "system notice"; placed above the hero before any app branding) and both were reverted after feedback that it looked out of place or was mistakable for an OS notification — this redesign is a different axis of change (smaller, not differently-shaped) and doesn't reopen that: same shape language as `TipBanner`, just sized down, still living in the ordinary card-flow position (first, right after the hero) rather than anywhere exceptional. The leading `AccountBalance` icon (a government building, not a warning triangle) is what's left of the old spelled-out "NATIONAL WEATHER SERVICE" eyebrow — same icon, so it still reads as "official source" without a dedicated label line. Tapping the strip opens `DetailSheet.Alert` directly when there's exactly one active alert, or `DetailSheet.AlertList` (a chooser) when there's more than one; a `SeverityDotCluster` — one small dot per alert, each colored by *that* alert's own severity, capped at 4 with a "+N" text fallback — renders next to the event name so someone can gauge overall risk ("one rust dot, one gold dot" = one severe hazard, one advisory) without tapping in. `ResolvedAlertCard` uses the identical strip treatment (sage green, checkmark icon) for visual consistency between the two — an odd pairing otherwise, a shrunk "urgent" indicator sitting above a full-size "all clear" card.

`DetailSheet.AlertList` used to stack every active alert's full `AlertDetailContent` (description, instructions, badges) in one non-scrolling `Column` — with 2-3 alerts this reliably exceeded the sheet's height and silently cropped the 2nd/3rd alert with no way to scroll to it, since `DetailSheetContent`'s root `Column` had no scroll modifier (`ModalBottomSheet` doesn't add one automatically; every *other* sheet type happened to fit within the sheet height by chance, which is why this was latent rather than immediately obvious). Fixed two ways: `DetailSheetContent` now wraps its root `Column` in `Modifier.verticalScroll(rememberScrollState())` as a general safety net for every sheet type, and `DetailSheet.AlertList` itself no longer shows full content at all — it's a tappable summary-row list (`AlertSummaryRow`: severity dot, event name, `alertTimeWindow()`), and tapping a row calls the new `DetailSheetContent(sheet, onAlertSelected: (WeatherAlert) -> Unit)` callback (wired in `WeatherScreen.kt` to `sheet = DetailSheet.Alert(it)`) to open that one alert's full view — since `ModalBottomSheet` stays open and only its content swaps, this reads as drilling into the chooser rather than the sheet closing and reopening.

`alertTimeWindow()` is a concise, single-line, never-truncated stand-in for NWS's own (often long) `headline` prose — e.g. `"12:00 PM – Jul 18, 8:00 PM"` — used by both the compact strip and `AlertSummaryRow`. The raw `headline` is often long enough to ellipsize before its "until X" time is visible, which made two distinct same-named alerts (see the `formatNwsTime` note above) look like duplicates at a glance; `headline` remains the fallback only when both `effectiveLabel` and `expiresLabel` are null. `AlertDetailContent` (the full single-alert view, reached via `DetailSheet.Alert` from either entry point) shows severity, `AlertBadge` pills for urgency/certainty (NWS's `"Unknown"` value is treated as absent, not rendered), description, instructions, and the effective/in-effect-until times. `alertColors(severity)` collapses the 5-value enum to 3 visual tiers (Critical = Extreme/Severe, Advisory = Moderate, Info = Minor/Unknown) — Critical is the one genuinely new hue in the app (warm rust/oxblood, not a clinical safety red); Advisory reuses the launcher icon's warm-gold; Info reuses the existing `tipColors()` RAIN tone verbatim.

**Alert resolution tracking:** `WeatherViewModel.trackAlertChanges()` runs after every successful fetch (foreground or background), diffing the current alert IDs against `PreferencesStore.getTrackedAlerts()` (a persisted `List<TrackedAlert>` — just `id` + `event`, not the full alert). Any previously-tracked ID missing from the new fetch is "resolved" and gets queued into `WeatherViewModel.resolvedAlerts` (in-memory `StateFlow`, not persisted across process death — an unresolved-but-undismissed notice simply won't reappear if the app is killed before the user sees it, since the tracked set is already overwritten to the current state). `ResolvedAlertCard` renders each one as a calm, dismissible, sage-green acknowledgment ("$event has ended") — deliberately opposite `AlertBannerList`'s severity styling, since this is reassurance, not an ongoing hazard. This exists because the app previously went silent when an alert cleared, giving no confirmation to a user who'd seen the earlier warning that the danger had actually passed (flagged by user feedback). Resolved cards render below any currently-active alert (an ongoing hazard always outranks an acknowledgment) but above `HourlyCard`. `selectPlace()`/`selectCurrentLocation()` call `resetAlertTracking()` to clear both the persisted and in-memory state on a location change — a tracked alert from the previous place isn't a real "resolution" for the new one.

**Tides (`WeatherData.tides: TideInfo?`, `data/model/TideModels.kt`, `util/TideStations.kt`, `data/remote/TideApi.kt`):** Today's high/low tide predictions from NOAA's Center for Operational Oceanographic Products and Services (CO-OPS, `api.tidesandcurrents.noaa.gov`) — free, public domain, no key, same "US-government API" precedent as NWS alerts. Null for every location that isn't coastal-or-tidally-influenced enough; the "Tides" tile (`buildMetricTiles()`) and its `DetailSheet` branch simply don't exist when it's null, same pattern as `AlertBannerList` not rendering when `alerts` is empty.

- **Coastal gate — `TideStations.nearest(context, lat, lon, maxKm = 10.0)`.** A bundled asset (`assets/tide_stations.json`, ~283KB, trimmed from NOAA's full ~1.9MB station metadata down to just `id`/`name`/`lat`/`lng` for all ~3500 US tide-prediction stations) avoids any network fetch just to check "is this coastal" — loaded once (`@Volatile` cached `List<TideStation>`), then a plain linear haversine scan (negligible cost at this station count, no spatial index needed). `WeatherRepository.getWeather()` calls this alongside the NWS alerts fetch, inside the same `coroutineScope`, wrapped in the same `runCatching { }.getOrNull()` defensive pattern — a station-lookup miss (returns null) or a NOAA fetch failure must never fail the overall weather fetch, exactly like NWS.
- **The 10km default is empirically chosen, not a round number.** NOAA's tide-prediction network follows tidal *rivers*, not just the open coast, and those rivers reach much farther inland than "coastal" ordinarily means to a user — a real station exists 3.6km from Trenton, NJ (the state capital, ~50 miles from the ocean, but the Delaware River is tidal that far upstream), which is *closer* than a genuinely coastal town like Ocean City, NJ measures to its own nearest station (4.8km). That gap proves distance-to-nearest-station alone cannot perfectly separate "coastal" from "far upriver but still technically tidal" — no threshold value excludes Trenton without also excluding some real coastal towns. 10km was picked because it correctly excludes this app's own known false positives (Franklin Park, NJ at 12.4km; Hillsborough Township, NJ at 17.7km) while every genuinely coastal town checked stayed under 5km. Deep-tidal-river state capitals like Trenton remain a known, unsolved edge case — a proper fix would need real coastline geometry (not just station proximity), which isn't in the bundled data. See `TideStations.nearest()`'s own doc comment for the full numbers.
- **`WeatherRepository.mapTide()`** turns the raw NOAA `predictions` (`type: "H"/"L"`, station-local time via `time_zone=lst_ldt`, height in the unit matching `UnitSystem.tideApiUnit`) into `TideInfo(stationName, events: List<TideEvent>)`. An empty predictions list (a station id that's valid but doesn't actually publish predictions — a real, observed NOAA inconsistency) is treated the same as "not coastal" rather than showing an empty tile.
- **UI:** `TideTile` (full-width `GlassCard`, same general shape as `MoonTile` minus the bespoke Canvas illustration) shows the next event's height + "$Type tide at $time". `TideDetailContent` (dispatched via `"Tides" -> ` in `DetailSheetContent`) lists every event for the day via `DetailRow`, plus a NOAA attribution line. `DetailSheet.Metric.tideEvents: List<TideEvent>?` carries the full list through, same pattern as `windGustMax`/`hourlySnowfall`.
- **Moon Phase tie-in:** the existing phase-cycle description in `MoonDetailContent` now also names spring tides (new/full moon — sun and moon aligned, the month's biggest tidal swings) and neap tides (first/last quarter — weakest swings), closing a real gap where only the neap-tide case was mentioned before.

**Daily forecast tips (`DayEntry.tips: List<WeatherTip>`, `WeatherRepository.buildDayOutlookTips()`):** Practical, day-specific "how to plan around this day" advice shown in `DetailSheet.Day` (via `TipBanner`, right after the hero H/L row, before the raw `DetailRow`s) for every entry in the 7-day forecast, not just today. Deliberately a fully independent function from `buildTips()` (the existing hero-`TipBanner` generator) even though the threshold logic overlaps (same hot/cold/windy/rain/snow detection) — `buildTips()`'s wording is hardcoded "today"-relative for its own night-rollover-aware use case, and reusing it verbatim for an arbitrary future day tapped open from the 7-day list would read as wrong ("Rain likely today" shown while looking at next Wednesday). `buildDayOutlookTips()` adds a second, more severe heat tier (`veryHot`, roughly NWS Excessive-Heat-Warning range: ≥100°F/38°C) beyond `buildTips()`'s single "hot" threshold, giving "stay indoors during peak hours" rather than just "carry water" — user-requested, to distinguish ordinary warm weather from genuine heat-safety territory. Capped at 2 tips per day, same as `buildTips()`.

**Today's `precipProbMax`/`isRain` are corrected for elapsed time; every other day isn't (2026-09-04 fix).** Open-Meteo's daily `precipitation_probability_max` and dominant `weathercode` describe the **full calendar day (00:00–23:59)**, which for *today* can describe a window that's already passed by the time someone checks the app — a real, user-reported bug: a 40% daily max and a "Light drizzle" day code from an already-elapsed morning still read as "Rain likely today — grab an umbrella" (both the hero tip and this day's own `DetailSheet.Day` tip) hours later, in a sky that was by then clear, with the forward-looking hourly forecast showing chance topping out at 17% and zero real rain amount in any remaining hour. Fixed at the data source in `mapToWeatherData()`'s `daily` build loop, not at each display site, so every reader of the field benefits: for `i == todayIndex` only, `dayPop` (feeding `DayEntry.precipProbMax`) is the max hourly `precipChance` across the hours still remaining today (bounded by the first `"12 AM"` hour label — the same boundary `MetricChart.dayChangeIndex` already uses), and the `code` fed into `buildDayOutlookTips()` for today is the live `currentCode` rather than today's historical dominant code (otherwise the corrected, now-honest percentage would still sit next to an unconditional "Rain likely" driven by the old code — confirmed as a real, distinct follow-on bug the first pass of this fix left in place). `buildTips()`'s current-day call gets the identical `currentCode`-over-historical-code treatment, with `tipsPop` now sourced directly from the corrected `today.precipProbMax` rather than a separately-computed 12-hour lookahead. Every *other* day in the list is deliberately untouched — they haven't started yet, so Open-Meteo's own full-day aggregate is exactly right for them, and the night-rollover case (tips switching to describe tomorrow) is untouched for the same reason. **Deliberately not fixed:** `DayEntry.icon`/`phrase` (the WMO glyph and "Light drizzle" label shown in the 7-day list itself) — recomputing a single "dominant condition for the remaining hours" is a fuzzier problem with more edge cases for less payoff than the number/tip-text fix, since the reported confusion was the percentage-plus-advice-text combination, not the icon. Because the fix lives on `DayEntry.precipProbMax` itself, `WeatherAdvisor`'s umbrella-type advice, `ChatRepository`'s AI weather-context brief, and `WeatherWidget`'s home-screen rain percentage (all three read this same field) are corrected automatically, with no separate changes needed in any of those files.

**Local time (`WeatherData.timezone`, `SavedPlace.timezone`, `util/LocalTime.kt`):** Live-updating "8:42 PM"-style clock shown under the location name in `CurrentHeader`, and next to every row (search results, saved places, current-location-when-selected) in the locations sheet. No new API call needed — both Open-Meteo's forecast response (already fetched with `timezone=auto`) and its geocoding response already return an IANA zone id (`"America/New_York"`) per result; these were parsed but never captured until this feature, so it's purely additive field-mapping (`OpenMeteoResponse.timezone` → `WeatherData.timezone`, `GeoResult.timezone` → `SavedPlace.timezone`, both nullable-with-default for the usual `ForecastCache`/persisted-JSON backward-compat reason). `util/LocalTime.kt`'s `rememberLocalTimeText(timezone: String?)` recomputes from `ZonedDateTime.now()` on a 30-second tick rather than caching a fixed UTC offset, so a session left open across a DST transition still reads correctly; returns null for a null/unrecognized zone id so callers just omit the row. The "Current location" row in the locations sheet only shows a time when it's actually the currently-loaded place (`selected == null`) — there's no geocoding result for "wherever the device is" ahead of a fetch, so its timezone isn't knowable otherwise. A place saved before this feature shipped has no local-time display until re-searched and re-added (same defaulting limitation as every other `= null`-defaulted field in this codebase).

**Haptic feedback (`util/WeatherHaptics.kt`, `PreferencesStore.getHapticFeedbackEnabled()`):** A single restrained haptic pulse fires when a fresh forecast loads for a genuinely notable condition — an active severe/extreme NWS alert (strongest pattern), a thunderstorm (an irregular, uneven-timing "rumble"), or heavy rain/snow (a few light "pitter-patter" clicks) — reusing the exact WMO codes `util/WeatherIcon.kt`'s `wmoText()` already labels "Thunderstorm"/"Heavy rain"/"Heavy snow"/"Violent showers", rather than inventing a new categorization. Most-severe-wins, same principle `WeatherBackground`'s `classify()` already uses for the animated scene. Ordinary/mild conditions — the common case — stay silent by design: this is meant to be felt occasionally for something worth noticing, not a buzz on every screen open, so it deliberately doesn't cover every WMO code the way the visual scene system does. `WeatherViewModel.load()` only fires it on a **foreground** load (cold start, a retry, or a location/unit change) — never the silent 30-minute periodic refresh or a pull-to-refresh, both of which can happen while the user isn't even looking at the phone. `VibrationEffect.createWaveform()` with an amplitude array has existed since API 26 (the app's own `minSdk`), so this needs no version fallback beyond `VibratorManager` itself (API 31+, with a `Context.VIBRATOR_SERVICE` fallback below that). Toggleable in Settings → Haptic Feedback (default on) — same on/off `OptionPill` pattern as the Widget Background toggle below — since any unsolicited vibration is undesirable for some users (accessibility, quiet environments). Uses the normal, no-runtime-prompt `VIBRATE` permission; no Data Safety impact. Not yet verified on a real device — pattern timings are a first pass, not user-tested.

**Widget:** `WeatherWidget` (Jetpack Glance) fetches weather independently at system-scheduled update intervals. `WeatherWidgetReceiver` wires it into the manifest (`android:exported="true"` — required for APPWIDGET_UPDATE broadcast delivery). `fetchFreshWeather()` resolves the device's live current location via `LocationProvider` every time — deliberately ignoring `PreferencesStore.getSelected()`, since the in-app "selected place" reflects whatever city is currently being *browsed* in the app, not "where I actually am" (this was a real, user-reported point of confusion before the fix: the widget mirrored the last city searched in-app). `WeatherViewModel` calls `WeatherWidget().updateAll(getApplication())` after every successful fetch to keep the widget in sync immediately.
- **Stale-while-revalidate** — `provideGlance()` reads `ForecastCache` synchronously up front, then uses `produceState(initialValue = LoadedWeather(cached...))` inside `provideContent { }` to render that cached forecast immediately as the first composition, while `fetchFreshWeather()` runs in the background inside the same `produceState` producer block; updating `value` on success recomposes with fresh data (`cachedAt = null`) and Glance pushes a second RemoteViews update. Fixes a real gap: on a cold process (reboot, app update, low-memory kill) `sharedRepository()`'s in-memory cache is empty too, so before this fix every cold start blocked on a full network fetch (25–50s) before showing anything, despite `ForecastCache` holding perfectly good recent data. A failed/no-location fetch simply leaves the cached (or empty) render as final, rather than overwriting it with something worse.

- **Shared repository instance** — `GlanceAppWidget` instances are created fresh per update, so `WeatherRepository`'s 30-minute in-memory cache only helps if the same instance survives across calls. `sharedRepository(context)` holds one `WeatherRepository` at file scope (double-checked locking via `sharedRepoLock`/`@Volatile sharedRepo`), shared by scheduled updates, every `onAppWidgetOptionsChanged` (i.e. every resize), and the manual-refresh action below — fixed a real bug where every single update did a fresh 25–50s forecast/air-quality/NWS fetch from scratch.
- **Manual refresh** — `RefreshButton` (a small "↻" glyph, inline in each tier's own header row — a corner-overlay `Image` sibling silently fails to render inside a `fillMaxSize()` `Box`, root cause not fully understood) triggers `RefreshAction`, which calls `sharedRepository(context).getWeather(..., forceRefresh = true)` to bypass the 30-minute cache, since the OS-enforced `updatePeriodMillis` floor (30 min) can't otherwise be sped up from the manifest side. Shown on every tier except `SMALL`.
- **Size-aware layouts** — `sizeMode = SizeMode.Responsive(setOf(SMALL, MEDIUM, TALL, WIDE, LARGE, XLARGE))`. Glance picks the largest declared breakpoint that fits the actual widget size; `WidgetContent` dispatches on `LocalSize.current`. Every breakpoint except `SMALL` is declared `MARGIN` (16dp) smaller than its true target size — confirmed empirically via the QA harness (see below) that Responsive matching needs real headroom, not just an exact-or-greater fit: a real host frame sized to a breakpoint's exact nominal dp value still fails to select it and silently falls back to the next tier down. This shrinks the layout canvas those tiers compose for too (Glance can't decouple "match against this size" from "lay out for this size"), so `MediumWidget`/`TallWidget`/`WideWidget`/`LargeWidget` are all tuned tight to fit the smaller MARGIN-adjusted canvas; `XLARGE` had slack in its original design and keeps its full padding.

  | Constant | DpSize (nominal, pre-MARGIN) | Cell grid | Content |
  |---|---|---|---|
  | `SMALL` | 110×50 dp | 2×1 | Emoji + current temp (22 sp Bold, `widgetTempColor`-tinted), centered |
  | `MEDIUM` | 110×110 dp | 2×2 | Location header + refresh + optional `AlertIndicator` + chrono-dynamic vertical stack (`MorningFocus`/`DaytimeFocus`/`NightFocus`) |
  | `TALL` | 110×220 dp | 2×4-ish | `MEDIUM` content plus a vertical 3-entry mini hourly list + staleness label — fills the extra height a narrow-but-tall placement would otherwise leave blank |
  | `WIDE` | 250×50 dp | 4×1 | `emoji temp° · location` + refresh, then either `AlertIndicator` (if an alert is active) or a 3-entry compact hourly row (`isDay`-aware glyph) |
  | `LARGE` | 250×110 dp | 4×2 | Optional `AlertIndicator` + `LargeHeader` (2-column, chrono-dynamic hero + refresh) + `HourlyStrip` (6 cells) + staleness label |
  | `XLARGE` | 300×250 dp | 5×5-ish | Optional `AlertIndicator` + `LargeHeader` + 6 full-detail `HourlyRow`s (time · icon · temp · feels-like · precip%) + staleness label |

  `weather_widget_info.xml` declares `minWidth="110dp"`, `minHeight="40dp"`, `targetCellWidth="2"`, `targetCellHeight="2"`, `resizeMode="horizontal|vertical"`, `updatePeriodMillis="1800000"` (30 min, the OS floor). A debug-only `WidgetQaActivity` (`app/src/debug/`) self-hosts `WeatherWidget` via a real `AppWidgetHost` for visual QA across every breakpoint without needing launcher drag/drop.

- **Chrono-dynamic content** — `currentTimeOfDay()` reads `Calendar.HOUR_OF_DAY`. `MEDIUM`/`TALL` (via the shared `MorningFocus`/`DaytimeFocus`/`NightFocus` composables) and `LARGE`/`XLARGE` (via `LargeHeader`) all branch on the result:

  | TimeOfDay | Hours | Focus |
  |---|---|---|
  | `MORNING` | 5–10 | Today's high temp (hero) + rain probability |
  | `DAYTIME` | 11–17 | Current temp (hero) + condition + H/L |
  | `NIGHT` | 18–4 | Tomorrow's H/L (hero) + tomorrow's condition |

  `MorningFocus`/`DaytimeFocus`/`NightFocus` must always be wrapped in their own `Column` at the call site inside `MediumWidget`/`TallWidget`, never inlined directly — each emits several direct `Text`/`Row`/`Spacer` elements with no wrapping container of their own, so inlining flattens them as siblings of the caller's other conditional children (alert indicator, hourly list, staleness label) and can exceed Glance's hard 10-child-per-container cap, which Glance silently truncates rather than crashing (a real bug, B29 in `IMPROVEMENTS.md`, hand-confirmed at 11–13 flattened children under real conditions).
- **Alert indicator** — `AlertIndicator` (small severity-colored dot + event name, `widgetAlertColor()` mirroring the in-app `alertColors()` tones since Glance has no `MaterialTheme` dependency) shown on `MEDIUM`/`TALL`/`WIDE`/`LARGE`/`XLARGE` when `data.alerts` is non-empty.
- **Condition-aware gradient background** — `WidgetContent` renders a small (4×200px, losslessly scaled via `FillBounds`) vertical gradient bitmap: `skyColor(data.currentIcon, data.isDay, c.isDark)` (the same shared source of truth as the in-app hero, `util/ConditionColors.kt`) fading into the widget's own Material You accent (`c.bgColor`), `remember()`-cached so it isn't re-rendered every recomposition. User-controlled opacity via Settings → Widget Background (`PreferencesStore.getWidgetTransparent()`): opaque by default, `TRANSPARENT_ALPHA = 0.55f` when enabled (an opt-in, not default, since text contrast was calibrated against a fully opaque background).
- **Real vector glyph icons** — `WidgetGlyph`/`renderGlyphBitmap` (`WidgetRendering.kt`) rasterizes the app's actual `WeatherGlyph` vector shapes (`drawWeather`/`glyphFor`, marked `internal` for reuse) to a bitmap shown via `Image`, replacing raw system emoji (which rendered inconsistently across OEM launchers). Uses `VividGlyphColors`, a deliberately more saturated widget-only palette, not the in-app muted one.
- **Temperature color** — `widgetTempColor(tempC, metric, isDark)` applies the same 6-bucket cool-to-warm concept as the in-app `DailyCard`'s `tempColor()`, with its own light/dark text-contrast-safe variant per bucket, to every hero and list temperature across all six tiers.
- **Shared hourly text sizing** — `HOURLY_TIME_SP` (11sp) / `HOURLY_TEMP_SP` (13sp) are used by every per-hour entry across `HourlyStrip` (LARGE), `HourlyRow` (XLARGE), and the upcoming-hour rows on `WIDE`/`TALL`, so the same reading is the same size regardless of which tier renders it.
- **Location name** — `widgetLocationName()` shows only the city (drops the ", State"/", Region" suffix `WeatherRepository.reverseGeocode()` produces) because Glance's `Text` has no ellipsize/overflow support at all (confirmed against library source — `maxLines` never calls `setEllipsize()`), so a long full name hard-clips mid-character on a real device instead of truncating cleanly.
- **Staleness label** — `stalenessLabel(cachedAt)` ("Updated Xm ago" / "Updated Xh ago") shown on `TALL`/`LARGE`/`XLARGE` when `LoadedWeather.cachedAt` is non-null, i.e. the widget is serving `ForecastCache` data rather than a fresh fetch.
- **Material You colors** — `resolveWidgetColors(context)` runs outside the composable (no `GlanceTheme` dependency needed). On API 31+ reads `android.R.color.system_accent1_100/700/900` via `ContextCompat.getColor` and detects dark mode from `context.resources.configuration.uiMode and Configuration.UI_MODE_NIGHT_MASK`. Light: accent1-100 bg + accent1-900 text. Dark: accent1-700 bg + accent1-100 text. Pre-API 31 falls back to the app's static dusty-blue palette. Returns `WColors(bg, bgColor: Color, textPrimary, textSecondary: ColorProvider, isDark: Boolean)` — `bgColor` (the raw `Color`, not just the `ColorProvider`) and `isDark` back the gradient background and temperature/alert color branching above. Only the `ColorProvider(Color)` single-argument overload is used — `ColorProvider(day, night)` does not exist in `glance-appwidget:1.1.0`.

**Launcher icon:** Adaptive icon (`mipmap-anydpi-v26/`) — warm-gold sun glyph (`#E0B15C`) on deep navy (`#0F1923`), with three concentric speech-wave arcs to the right of the sun (radii 20/25/30 dp, fading opacity) representing the "speak" dimension. XML-only; no PNG fallbacks needed since `minSdk = 26`.

**WMO weather codes** are mapped to emoji and text in `util/WeatherIcon.kt`. All temperature/wind/precip values in `WeatherData` are stored in the user-selected unit (they come back from Open-Meteo already converted); `WeatherAdvisor` converts back to metric internally for threshold comparisons.

**`HourEntry`** carries `hourLabel`, `tempC`, `icon` (WMO code), `isDay: Boolean`, and `precipChance: Int?`. `isDay` is computed per-hour in `WeatherRepository` via ISO-string comparison (`hourTime >= sunriseStr && hourTime < sunsetStr`) against the day's sunrise/sunset strings from the daily block. `HourlyCard` passes `h.isDay` to `WeatherGlyph` so each hour renders the contextually correct day or night icon. `HourlyCard` wraps its `LazyRow` in a `Box` with `rememberLazyListState`; a 28dp right-edge gradient fade (`Color.Transparent → colorScheme.surface`) is always overlaid as a scroll affordance, and a 20dp left-edge fade appears once `firstVisibleItemIndex > 0` or `firstVisibleItemScrollOffset > 0`.

## UI theme & branding

**Logo:** Two-tone text wordmark — an `AnnotatedString` in `WeatherScreen.kt` rendering `"sky"` in `TextSecondary` and `"speak"` in `TextPrimary`, at 20 sp, `FontWeight.Light`, `letterSpacing = 5.sp`. The color split is subtle in light mode (muted slate → near-black) and more expressive in dark mode (slate → near-white). Colors are captured as local vals before the `buildAnnotatedString` block so they are read in composable scope. Do not reintroduce image assets or collapse the two spans into a single `color` parameter.

**Colour scheme (`ui/theme/Theme.kt`):**
- Light: background `#F4F1EB` (warm cream), surface `#FDFCFA` (barely warm white), primary `#6B86A3` (dusty blue).
- Dark: background `#0F1923` (deep navy), surface `#1A2530`, primary `#7FA3C2`.
- `AppBackground`, `TextPrimary`, `TextSecondary` are `@Composable` vals in `WeatherComponents.kt` resolved from `MaterialTheme.colorScheme` — always use these rather than hardcoded colours.

**Condition gradient (`conditionGradient` in `WeatherComponents.kt`):** A `@Composable` function that maps a WMO weather code + `isDay` flag to a two-stop `List<Color>`. The first stop is a sky tone (blue for clear day, indigo for thunder, slate for rain, etc.); the second stop is always `MaterialTheme.colorScheme.background` so the gradient fades seamlessly into the card area. Additionally, `Calendar.HOUR_OF_DAY` is read and the sky color is `lerp`-blended with a time-of-day tint: 5–6 AM → warm apricot (`#E8936A`, 18%), 5–6 PM → amber (`#D4A44C`, 15%), 7–8 PM → dusty violet (`#A0668A`, 20%). All other hours receive no tint. Used as the base layer of `WeatherBackground` (stretched to the full screen, with particle scenes drawn on top) via `Brush.verticalGradient`. Dark-mode stops are deliberately lighter/more saturated than a naive darkened version of the light-mode stop — the dark background (`#0F1923`) is itself very dark, so a naive darken puts most conditions within a few RGB steps of the background and the gradient reads as flat/invisible. Each dark stop is calibrated for a visible lift off the background, same as the light-mode stops are clearly lifted off the cream background.

**`GlassCard` (`ui/components/WeatherComponents.kt`):** The shared card wrapper. Shadow adapts per theme: `1 dp` in light (airy), `6 dp` in dark (depth). Border opacity likewise adapts. All major content sections (hourly, daily, metric tiles) use `GlassCard`. Fill is always opaque `colorScheme.surface`, overridable via the `fill` param (e.g. `AlertBannerList`'s severity tint) — see `WeatherBackground` above for why a translucent fill over the animated background was tried and reverted.

**Metric tile system (`MetricsGrid` in `WeatherComponents.kt`):** Six distinct composables:

For Moon Phase, `gaugeFraction` stores the phase fraction (0.0 = new moon, 0.5 = full moon) as computed by `MoonCalculator.phase()`.

**`MetricTileData.advisory`:** Short (2–4 word), tile-length "so what does this mean for me today" callout, teaching a metric's meaning in the moment with no tap required — distinct from `description`'s full-sentence version shown in the detail sheet. Populated only where a natural "what should I do" phrase already exists: UV Index (e.g. "Wear SPF", mirrors `uvAdvice`'s tiers), Air Quality (e.g. "Great for outdoors", mirrors `aqiAdvice`'s tiers), Wind (e.g. "Breezy", derived from today's forecast peak gust — `DayEntry.windGustMaxKmh`, from Open-Meteo's `wind_gusts_10m_max`), and Humidity (e.g. "Comfortable", derived from `WeatherData.dewPointC` — from `dew_point_2m` — converted to true Celsius via `toCelsius()` before threshold comparison, same unit-ambiguity pattern as `tempColor()`). `null` elsewhere (Pressure, Visibility, Sunrise, Moon Phase, Feels like, Precipitation) — those don't get a placeholder just to fill the slot.

**`MetricChart.dayChangeIndex`:** `Int?` field on `MetricChart`. Set by `buildMetricTiles` to the index of the first `"12 AM"` label in `d.hourLabels` (null if data doesn't span midnight). Consumed by `SparklineTile` to draw a dashed vertical line at the day boundary, and by `WindDetailContent`, `FeelsLikeDetailContent`, and `PrecipDetailContent` to draw the same marker in their detail-sheet charts. The time-axis label at that index is replaced with `"tmrw"` in accent color.

**`SunTile` data encoding:** `MetricTileData.value` holds the sunrise time string. `MetricTileData.sub` encodes `"Sunset HH:MM|TomorrowRise HH:MM"` — `SunTile` splits on `|` and parses each key-value pair. `parseTimeHour(time: String?)` handles both 24-hour strings and 12-hour AM/PM strings.

**`MoonTile` / `drawMoonPhase`:** `drawMoonPhase(center, r, phase, litCol, darkCol)` is a private `DrawScope` extension in `WeatherComponents.kt`. Draws the illuminated lunar disk using an arc-based path: a semicircle on the lit side closed by an ellipse arc representing the terminator. `termX = r * cos(phase * 2π)` gives the terminator x-offset. Waxing (phase < 0.5): left shadow half-circle + conditional ellipse; waning (phase ≥ 0.5): right shadow half-circle + conditional ellipse. Short-circuits to solid dark disk at new moon (phase < 0.02 or > 0.98) and solid lit disk at full moon (phase 0.48–0.52).

**Fluid day-detail transition (2026-09-04, replaced `DetailSheet.Day`):** Tapping a day in the 7-day forecast no longer opens a `ModalBottomSheet` — it expands that row into a full-screen detail view via a Compose shared-element transition (`SharedTransitionLayout`/`AnimatedContent`, `@OptIn(ExperimentalSharedTransitionApi::class)`), matching `PREMIUM_UX_ROADMAP.md`'s Medium-tier "Fluid Layout Transitions" item. `DetailSheet.Day` was removed entirely (its only construction site was `DailyCard`'s tap handler) rather than left as unused dead code alongside the new mechanism. `WeatherContent` holds `expandedDay: DayEntry?` and wraps its whole body in `SharedTransitionLayout { AnimatedContent(targetState = expandedDay) { day -> ... } }`: the `null` branch is the existing screen (now factored into a private `WeatherContentBody`, unchanged in content, just parameterized to take `sheet`/`onSheetChange` instead of owning that state directly since it's no longer the sole state holder in this function), and the non-null branch renders a new `ExpandedDayDetail` composable. Both `DailyCard`'s tapped `Row` (`Modifier.sharedBounds(rememberSharedContentState(key = "day-${day.dayLabel}"), animatedVisibilityScope)`) and `ExpandedDayDetail`'s root `Column` carry the identical key, which is what makes the row visually grow into the full-screen container rather than a new screen simply appearing — `dayLabel` ("Today"/"Sat"/.../"Thu") is guaranteed unique within one 7-day fetch, so no key collision risk. `DailyCard` became a `SharedTransitionScope` extension function (`fun SharedTransitionScope.DailyCard(...)`) taking an explicit `animatedVisibilityScope: AnimatedVisibilityScope` parameter — Kotlin doesn't support two receivers without opting into context receivers, so the caller threads both scopes through via `with(this@SharedTransitionLayout) { DailyCard(..., animatedVisibilityScope = this@AnimatedContent) }` rather than that experimental compiler feature. The actual day content (date, glyph, phrase, H/L, tips, `DetailRow`s) lives in a shared `DayDetailBody(day, windUnit, precipUnit)` composable so neither the old sheet path nor the new full-screen path duplicates it — currently only the new path calls it, since the sheet path it replaced is gone. `ExpandedDayDetail` adds its own back arrow (`Icons.AutoMirrored.Filled.ArrowBack`) and a `BackHandler(enabled = expandedDay != null) { expandedDay = null }` so the system back button/gesture closes the expanded view instead of leaving the screen or exiting the app. Every other detail sheet (Metric, Alert, AlertList, Forecast) is untouched — still the ordinary `ModalBottomSheet` path, exactly as before; this redesign is scoped to the one day-row interaction, not applied app-wide. Verified live on-device: tapping a day row grows into the correct full-screen detail (confirmed for both "Today" and "Saturday, Sep 5", each showing correct, distinct data), and the back arrow returns to the list at its prior scroll position, preserved via `WeatherContentBody`'s `rememberScrollState()` surviving the `AnimatedContent` transition.

**Same-day follow-up fix — the "overlapping text" was a real bug, not a screenshot artifact.** The first on-device report (not just a screenshot caught mid-flight, as first assumed) described a visible flash during the transition. Root cause: `AnimatedContent` had no custom `transitionSpec`, so it defaulted to cross-fading the *entire* outgoing screen with the *entire* incoming screen simultaneously — both full screens' text genuinely blended on top of each other for the transition's duration. Fixed with `transitionSpec = { EnterTransition.None togetherWith ExitTransition.None }`, so only the `sharedBounds`-tagged element (the row growing into the header) visibly animates; everything else in each screen appears/disappears immediately rather than fading through the other screen. Separately, neither `sharedBounds` call specified a `resizeMode`, so both defaulted to `RemeasureToBounds()` — continuously re-laying-out the child at every intermediate size, which looks janky when (as here) the row's compact `Row` layout and the destination's full `Column` layout share no structure. Both calls now specify `resizeMode = SharedTransitionScope.ResizeMode.scaleToBounds()` (lowercase — the API was renamed from the capitalized `ScaleToBounds()` between the Compose Animation library versions; this project resolves 1.11.4 via its BOM, not the version some documentation/examples reference), which renders each end's own layout once and scales/crossfades between them instead of relaying out mid-animation. Re-verified live on-device after the fix: no ghosting/overlap in a same-timing screenshot.

**Per-day hourly breakdown (2026-09-04) — fills the space, guaranteed consistent with the main screen.** `ExpandedDayDetail` left roughly a third of the screen empty for a typical day (date + glyph + one tip + six `DetailRow`s rarely fill a full phone screen) — user-reported, along with the observation that Open-Meteo's hourly response actually covers all 7 days, not just the ~24 hours `WeatherData.hourly` keeps. `DayEntry.dayHourly: List<HourEntry>` (defaults `emptyList()`, usual cache-back-compat reason) now carries that day's own full 00:00–23:00 local hourly breakdown, rendered via a new `DayHourlyStrip` composable (a horizontally-scrollable strip, same right/left scroll-fade affordance as `HourlyCard`, fading into `AppBackground` specifically since this strip sits on `ExpandedDayDetail`'s flat page rather than inside a `GlassCard`) placed in `DayDetailBody` before the summary `DetailRow`s. **Critical constraint, explicitly required and verified:** any hour that appears in both `WeatherData.hourly` (the main screen's "next 24 hours from now" strip) and a day's own `dayHourly` — which happens for Today's remaining hours, and would happen for a next day if the 24-hour window reaches that far — must show byte-identical values in both places, not just approximately similar ones. This is guaranteed **by construction, not by coincidence**: `WeatherRepository.hourEntryAt(i): HourEntry` is a single function extracted from what was previously `hourly`'s inline `.map {}` lambda, and both `hourly` (`window.map { hourEntryAt(it) }`) and each day's `dayHourly` (`hourTimes.indices.filter { hourTimes[it].startsWith(dayDate) }.map { hourEntryAt(it) }`) call this same function against the same raw index into the same underlying Open-Meteo arrays — there is no second, independently-written computation that could quietly drift in rounding or field mapping. `HourColumn` (the per-hour glyph/temp/precip visual, previously inlined in `HourlyCard`'s `LazyRow` items) was likewise extracted into one shared private composable used by both `HourlyCard` and `DayHourlyStrip`, so the two hourly displays aren't just numerically identical but pixel-identical for a shared hour too. Verified live on-device by direct side-by-side comparison: the main screen's "Next 24 Hours" card and Today's own expanded-detail hourly strip, scrolled to the same hours, showed exactly matching temperature, precipitation chance, icon, and "Now" highlighting for every one of 5 compared hours (Now, 8 PM, 9 PM, 10 PM, 11 PM).

Tornado/Hurricane are handled separately via `alerts` (not `code`), since `conditionGradient` has no alert awareness — `WeatherBackground` layers its own dark overlay rect for those scenes independent of the base gradient.

**versionCode 15 — two more rounds on this same system, both from a real user report of H/L/feels-like being hard to read in light mode that persisted across multiple real locations/conditions:**
1. **`skyColor()`'s rain/snow/fog branches (`ConditionColors.kt`) didn't check `isDay` at all**, unlike thunder (deliberately dark regardless of daylight, by design) — only `isDark` (app theme). So a rainy/snowy/foggy *night*, in light theme, rendered the exact same bright pastel tone as the equivalent *day* (`0xFFBFD4E6` for rain, etc.) — a real, previously-unfixed gap distinct from the Overcast case above, since Overcast (code 3) isn't in any of those three ranges and was already covered by the `!isDay` catch-all. Dark theme's existing values for these three ranges were left unchanged (already dark enough to read fine at any hour — the mismatch is a light-theme-only problem). Fixed with dedicated light-theme night variants (`0xFF1E2E44` snow / `0xFF17293C` rain / `0xFF20262C` fog) sitting between the bright daytime tone and the generic night navy. `heroBackdropIsDark()`'s matching three branches changed from unconditional `false` to `!isDay` so the hero text pair flips correctly for the new dark night variant.
2. **The claimed-fixed `0xFF3F5670` secondary tone was still genuinely under WCAG's 4.5:1 floor** — this file's own prior text said "measures ~4.3–5.6:1" and named Overcast as the *worst* case, but 4.3:1 is *below* 4.5:1; the value had been carried over from a different context (`tipColors()`'s solid-tint pill) without ever being re-verified against Overcast's actual near-gray sky. Replaced with a dedicated `0xFF233A4F` (~6.5:1 against that same Overcast gray, real margin instead of another borderline value) — see the paragraph above.
3. **Even with (2)'s fix, the user still reported it hard to read across multiple different locations/conditions** — the remaining gap: `WeatherBackground` is an *animated* scene (moving rain/cloud/snow particles), not the flat color any contrast-ratio math assumes, so a locally lighter patch behind a specific letter can still wash out a well-chosen flat color. Added a subtle `Shadow` (`Color.Black` at 35% alpha, 1dp offset, 6px blur) to just the H/L and feels-like `Text`s specifically — the two lines actually reported as hard to read — giving a guarantee flat-color contrast can't: legible against literally any pixel behind it. Not applied hero-wide, to avoid the risk/cost of touching elements that weren't reported as a problem.

**Hero font weight (`heroWeight` in `WeatherComponents.kt`):** A second, related light-theme-only issue, user-reported by direct comparison with dark mode: even with `heroTextColors` fixing contrast, the hero's already-light weights (`Thin` display numeral, `Light` wordmark, `Normal` body text) read as visually "weak" in light theme specifically — a real optical effect (irradiation: a bright surround makes a dark glyph look thinner than the identical glyph reversed light-on-dark), not a rendering bug, so dark theme's light-on-dark hero text at the same nominal weights reads fine. `heroWeight(base: FontWeight)` steps every hero text weight up one level (`Thin→ExtraLight`, `Light→Normal`, `Normal→Medium`, `Medium→SemiBold`) in light theme only, returning `base` unchanged in dark theme. Applied to every `Text` in `CurrentHeader` (location, condition, temperature, H/L, feels-like, lookahead pill) and the "sky\|speak" wordmark in `WeatherScreen.kt` — the same set of elements `heroTextColors` covers, since both fixes address the same hero-vs-background legibility concern. Verified on-device: light-mode hero at Franklin Township, NJ visibly reads heavier after the change (before/after screenshots), dark mode confirmed pixel-identical in weight (unchanged code path).

**Lookahead pill (`WeatherData.headline`):** `WeatherData.headline` is `String?` — populated by `WeatherRepository.buildUpcomingHeadline()` when hourly data is present, null otherwise. `buildUpcomingHeadline()` itself always returns a non-null `String`. `CurrentHeader` falls back to `data.comparedToYesterday` when `headline` is null. Operates on the raw `HourlyBlock` + `nowIndex` (the exact position of the current hour in the full 7-day API array) so the scan always starts from the true "now" and naturally crosses into the next day. Scans the next 12 raw hourly entries (`nowIndex+1` .. `nowIndex+12`) for the first significant condition change — Thunderstorm, Snow, Rain, Freezing rain, Drizzle, Fog — relative to the current WMO code. Appends a wind note when the next-12-hour max exceeds 40 km/h / 25 mph. Trusts WMO codes directly; only light drizzle (51–57) requires a ≥30% precipitation-probability floor. Falls back to a dominant-condition summary over the next 6 hours (rather than `null`) when no significant change is detected — but only asserts a specific condition (e.g. "Clear skies for the next few hours") when one WMO code holds a real majority (≥60%) of those 6 hours; otherwise returns "Mixed conditions over the next few hours." rather than guessing off a bare plurality.

**Glanceable AI ring + tap-to-expand summary (2026-09-04, `PREMIUM_UX_ROADMAP.md`'s Medium tier):** The pill above is now the tap target for a larger, dedicated view of the same headline — tapping it opens `DetailSheet.Forecast(headline, pressureDropAlert)` (a new `DetailSheet` variant, rendered via the existing `ModalBottomSheet`/`DetailSheetContent` plumbing, no new sheet mechanism introduced) showing an `Icons.Filled.AutoAwesome` sparkle icon in `Cyan` (the same icon/color the chat FAB already uses, for a consistent "this is the AI" visual language), a "Forecast Insight" title, and the headline at a larger, more legible size than the compact pill. Separately, `WeatherData.pressureDropAlert: Boolean` (`WeatherRepository`, computed as a sustained drop of ≥3 hPa between `hourlyPressure[0]` — "now" — and the lowest value across the next 6 hourly entries; defaults `false` for the usual cache-back-compat reason) drives a subtly pulsing ring drawn behind the hero temperature — a real, data-backed "something may be changing" signal, not decorative, and deliberately not gated on any per-activity/suitability language (see the "Considered and dropped" entry in `PREMIUM_UX_ROADMAP.md` for why that specific framing was ruled out elsewhere). The ring only renders when `pressureDropAlert` is true — the common (no-anomaly) case renders the temperature exactly as before this feature existed, no layout change. When `pressureDropAlert` is true, the Forecast sheet also appends a plain, data-only sentence about the pressure trend (not framed as advice or a safety claim). Verified live on-device: tapping the pill opens the sheet correctly with the headline text; the ring itself wasn't visually verified on a real device, since no genuine ≥3 hPa/6h drop occurred during testing — the no-anomaly path (ring absent) was confirmed correct.

**`TipBanner` source data:** Tips are generated by `WeatherRepository.buildTips()`. At night (`isDay = 0`) the tip day switches to the next daily entry so tips reflect upcoming conditions rather than the day just passed. The precipitation probability passed to `buildTips` is always `max(tipDay.precipProbMax, maxPrecipChanceInNext12Hours)` to capture short-range rain even when the daily summary hasn't rolled over yet.

**Daily forecast precipitation probability:** Shown inline below the WMO glyph in `DailyCard` rows, using the same `Indigo` style as the hourly row, whenever `precipProbMax >= 40` — the "balanced" meteorological threshold where rain crosses from a slight chance into a real one, deliberately not `precipProbMax > 0`. Originally gated on `day.icon in 45..99` (the day's dominant WMO code) instead, but that was a poor proxy: a day's own code is only loosely correlated with its actual probability number, so a real 6–10% chance on an Overcast day (code 3, outside that range) hid the badge while a technically precip-coded day with the same low real chance showed it — user-reported as a real inconsistency against the unconditional "Chance of rain" `DetailRow` in `DetailSheet.Day`, which always shows the raw number regardless of icon. Gating on the number itself instead means the list and detail sheet can no longer contradict each other: whenever the list shows a badge, it matches the detail sheet exactly, and whenever it doesn't, it's because the real chance is genuinely below the threshold, not because of an unrelated code. Deliberately a lower bar than `buildTips()`'s `pop >= 50` "likely" threshold — a quiet visual hint at 40%+, a bold "grab an umbrella" claim reserved for 50%+.

**Tapping a `DailyCard` row** opens `DetailSheet.Day(day, windUnit, precipUnit)`. Its content (in `DetailSheetContent`) renders `day.tips` (see "Daily forecast tips" above) via `TipBanner` right after the hero glyph/phrase/H-L row and before the plain `DetailRow`s (sunrise, sunset, max UV, chance of rain, precipitation, max wind) — conclusion first, numbers after.

**`DailyCard`'s temperature range bar (`TempRangeBar`):** A `Canvas`-drawn horizontal bar per day, positioned between the low and high temperature labels — the filled segment spans `weekMinC`–`weekMaxC` proportionally and is colored via `tempColor()`, a 6-stop cool-to-warm gradient. `DailyCard` derives `val metric = data.windUnit == "km/h"` (rather than adding a new `WeatherData` field, since `windUnit` already reliably encodes the unit system) and passes it through to `TempRangeBar`, which converts `low`/`high` to true Celsius via `toCelsius()` before calling `tempColor()` — see the Key invariants entry on unit-ambiguous "C"-suffixed fields.

**`AttributionFooter` (`ui/components/WeatherComponents.kt`):** Shows the Open-Meteo CC BY 4.0 attribution line, plus a tappable "☕ Support the developer" line beneath it in `MaterialTheme.colorScheme.primary` that opens a donation page via `LocalUriHandler.current.openUri(...)`. This was the first use of `LocalUriHandler` in the codebase. The destination URL lives only in this composable's source — do not duplicate it in documentation or comments elsewhere.

## Key invariants

- `WeatherData` fields store values **in the user's current unit system** (not always metric). This is set at fetch time via `UnitSystem.apiTemp`/`apiWind`/`apiPrecip` passed to Open-Meteo, and the unit labels (`windUnit`, `precipUnit`, `visibilityUnit`, `tempLabel`) travel alongside.
- The 30-minute cache in `WeatherRepository` is in-memory only and scoped to the process. Widget updates bypass the app's ViewModel and create their own `WeatherRepository` instance.
- OpenRouter key resolution: `PreferencesStore.getOpenRouterKey(buildDefault)` returns the on-device key first, falling back to the build-time `BuildConfig` value. Always pass `BuildConfig.OPENROUTER_API_KEY` as the fallback.
- Drawable resource names must be all-lowercase (`a-z`, `0-9`, `_`) — Android's AAPT2 rejects uppercase characters.
- `MetricChart.dayChangeIndex` must be derived from `d.hourLabels.indexOfFirst { it == "12 AM" }.takeIf { it >= 0 }` in `buildMetricTiles` and passed to every `MetricChart` constructor — do not hardcode or omit it.
- `parseTimeHour` handles both 24-hour (`"18:30"`) and 12-hour AM/PM (`"6:30 PM"`) formats. Always use it when parsing sunrise/sunset strings from `WeatherData` inside a `DrawScope` or Canvas block.
- Any threshold logic keyed off a `WeatherData`/`DayEntry` "C"-suffixed field (e.g. `tempColor()` in `DailyCard`'s temperature range bar) must convert to true Celsius first via a helper like `toCelsius(v, metric)` (mirrors `WeatherAdvisor.toC`) — the field only *sounds* like it's always Celsius. Skipping this previously made the 7-day forecast bar render a uniformly hotter (reddish) color in °F than the identical real temperatures showed in °C, since raw Fahrenheit numbers are always larger.
- **Snowfall is never in `precipUnit`.** Verified live against Open-Meteo: `precipitation_unit=mm` (this app's METRIC setting) leaves `snowfall`/`snowfall_sum` in **cm** — a real 10x unit mismatch, not just a cosmetic label difference. Only `precipitation_unit=inch` (IMPERIAL) converges snowfall to `"inch"` too, matching `precipUnit`. Always pair a snow amount (`WeatherData.currentSnowfall`, `hourlySnowfall`, `DayEntry.snowfallSum`) with `WeatherData.snowUnit` (`UnitSystem.snowLabel`: `"cm"` metric / `"in"` imperial) — never `precipUnit`.
- `WeatherData.precipMm` (current-hour total) and `currentRainMm`/`ChatRepository`'s "rain:" line are **rain+showers only**, not the same figure — `precipMm` is Open-Meteo's `precipitation`, which bundles rain+showers+snow water-equivalent together, so it alone can't tell a caller whether it's actually raining or snowing. Anything that needs to know the *type* (metric tile, chat context, `WeatherAdvisor`) must read `currentSnowfall`/`currentRainMm`/`hourlySnowfall`/`hourlyPrecipAmount` instead, never infer type from `precipMm` or from `precipChance`/`precipProbMax` (both are `precipitation_probability`, which doesn't distinguish rain from snow at all — a high reading only means "some precipitation is likely," and treating it as "rain" was a real bug in `WeatherAdvisor.umbrella()` that told people to grab an umbrella on snow days; fixed via the `Ctx.isSnowy` check, computed from real `currentSnowfall`/`hourlySnowfall` data with an `isSnowOrIce(code)` fallback).
